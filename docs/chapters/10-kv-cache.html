III. The cache · Chapter 10

Why generation is slow and memory-hungry

Decoding one token at a time means the model must remember every key and value it has already computed, and that memory is the real cost of long context.

The measured request profile

The mean request in this engine's sample window arrived carrying 130,659 tokens of prompt and asked for 607 tokens back. The window covers 98 requests counted by the tensorfold:request_latency_seconds_count counter, scraped on 2026-10-31. Over those requests the engine averaged 3.33 seconds of prefill and 8.38 seconds of decode, with 3.46 seconds to first token. Prefill ran at 39,237 tokens per second. Decode ran at 59.1.

The prefill figure checks against the prompt length. 130,659 tokens divided by 39,237 tokens per second gives 3.33 seconds, which is the mean prefill duration. Time to first token starts when the request arrives, so it includes admission wait, tokenization, the prefill pass, and the first decode step that emits a token. The mean is 3.46 seconds against a mean prefill of 3.33, which leaves 0.13 seconds for admission, tokenization, and that first step. Decode divides differently. 607 tokens in 8.38 seconds is about 72 tokens per second per request, higher than the 59.1 single-stream figure because the window mixes requests that ran concurrently and shared weight reads.

Why decode advances one token at a time

Prefill runs at 664 times the decode rate on this pair, and the gap follows from the shape of the computation rather than from a hardware defect.

A language model produces one token per forward pass. It reads the sequence so far, produces a distribution over the vocabulary at the final position, samples from it, appends the sample, and starts again. Token t+1 depends on token t, and token t did not exist when the pass began, so the loop cannot be unrolled in the naive exact-sampling sense — each token must be conditioned on the verified prefix. Techniques such as speculative decoding can propose several draft tokens and verify them in one target forward pass, partially breaking this dependency, but the target model still advances one verified block at a time. in the naive exact-sampling sense — each token must be conditioned on the verified prefix.

A 607-token reply is 607 forward passes, each conditioned on everything before it.

The naive way to run that loop feeds the whole sequence in every time. Pass one sees 130,659 tokens, pass two sees 130,660, and pass 607 sees 131,265. Attention inside each pass lets every position attend to itself and all preceding positions, so the number of comparisons in one pass grows with the square of the sequence length Summed over the reply, the total grows as the reply length times the square of the prompt length. For a long prompt that product is catastrophic. The model would re-derive the same key and value vectors for the same 130,659 positions 607 times and discard each set.

What the KV cache stores

The fix is to keep them. Inside every attention layer, each position produces a query, a key, and a value. The query is consumed once, in the pass that created it. The key and the value are what later positions compare against and read from. So the cache stores exactly those two, per layer, per position, per key-value head, which is why it is called the KV cache and not the QKV cache. The omission of the query is the whole point. It is the one tensor with no future.

To see the shapes, take one layer with h query heads, g key-value heads, and head dimension d. The hidden state at a position projects to a query of h×d numbers, a key of g×d numbers, and a value of g×d numbers. When g equals h the layer is ordinary multi-head attention. When g is smaller, several query heads share one key-value head, which is grouped-query attention. The cache holds the keys and values only, so its size per position per layer is 2 × g × d × b bytes, where b is the number of bytes per element.

With the cache, pass k computes keys and values for one new position, then attends that position's query against the stored keys of every previous position. The feed-forward work per step is one token's worth. The attention work per step is a read over the cache. Generating n tokens after a prefill of length p costs roughly one prefill plus n small steps instead of n full passes. The transformer paper described the decoder as autoregressive from the start (Vaswani et al. 2017), and caching the keys and values is the standard way to run that decoder.

The arithmetic behind the cache size

Now the size. Multiply the per-position figure by the number of positions. The engine's config script records 0.9 GiB per rank for 1,048,576 positions, so raising the pool from 262,144 to 1,048,576 adds 786,432 positions and costs 0.9 × 786,432 / 1,048,576 = 0.675 GiB per rank, which the deployment rounds to 0.68. That works out to 0.675 GiB divided by 786,432 positions, or about 922 bytes per position per rank. Substituting into the formula gives 2 × L × g × d × b = 928 for the layer count L and element size b this model uses.

At the mean prompt length the cache is 130,659 × 928 bytes, or about 121 MB per rank. Four streams carrying that prompt would hold 484 MB of cache between them, and every decode step re-reads all of it. The multiplier on g matters here. A model with 32 query heads and 8 key-value heads pays one quarter of what the same model would pay with 32 key-value heads, because the cache scales with g and not with h. That ratio is why grouped-query attention became standard, and it is why the 0.68 GiB figure is small enough to be practical.

Positions, rows, and admission

The pool itself is a shared resource. It holds 262,144 positions across 4 concurrent streams. Positions, tokens, and rows are three different things and the rest of this chapter depends on keeping them apart. A token is a unit of text. A position is one slot in the pool holding that token's key and value for every layer. A row is one entry in a decode batch, and the kernel processes at most 16 rows per step, set by ROUND_ROWS=16.

The allocator is paged, following the design Kwon and colleagues described for vLLM in 2023. The pool is divided into fixed-size blocks, typically 16 positions each, and a block table maps each request's logical positions onto physical blocks. A request that grows does not need contiguous space, so the pool does not fragment the way a contiguous allocator would. The analogy to virtual memory is exact. The operating system maps contiguous virtual pages onto scattered physical frames through a page table, and the serving engine maps contiguous logical positions onto scattered physical blocks through a block table. That is what chapter 13 means by the page table fixing the allocation problem.

Admission reserves the reply budget before generation starts. The scheduler admits a request only if the pool can supply blocks for the prompt plus MAX_TOKENS, which defaults to 32,768. The reservation is worst-case, so a request never stalls mid-reply waiting for cache. With four streams an equal share of the pool would be 65,536 positions each, though the pool is shared and a stream may use more if others use less. and the reservation subtracts 32,768 for the reply, 16 for the round batch, and 2 for alignment, leaving 32,750 usable positions per stream. A mean request needs 130,659 positions for its prompt alone, so it cannot be admitted at concurrency 4 at all.

At concurrency 1 the ceiling is 262,144 − 32,768 − 16 − 2 = 229,358 positions, and the prompt needs 130,659 positions against the 229,358 ceiling, leaving 98,699 positions spare; the 607-token reply is already covered by the 32,768 reservation. It fits with room to grow.

Batching, bandwidth, and the prefix cache

Decode is not compute-bound. The GPU here runs at 2,197 MHz observed under load against a 3,003 MHz silicon ceiling (nvidia-smi clocks.sm, 2026-10-31; GB10 documentation). At that clock it can retire an enormous number of multiply-adds per second. But one decode step does one token's worth of arithmetic against a cache that may be hundreds of thousands of positions long, and against every weight in the model. Count the arithmetic intensity. Each weight participates in one multiply-add for the single new token, which is two floating-point operations, and it must be read from memory once, which is two bytes in half precision. That is one FLOP per byte.

The KV read adds bytes and roughly proportional arithmetic—about one FLOP per byte in FP16—so it keeps the overall intensity near one rather than lowering it So the intensity sits near one, far below the machine's balance point of peak FLOPs divided by bandwidth.

The limit is therefore 273 GB/s of unified LPDDR5X bandwidth, shared between CPU and GPU, out of 111.5 GB of total unified memory (111,515,771,428 bytes from the device memory metric; bandwidth from the NVIDIA DGX Spark hardware guide). Divide bandwidth by token rate. 273 GB/s divided by 59.1 tokens per second is 4.62 GB of traffic per token. The cache and the weights both have to come past the arithmetic units on every step, and a faster clock buys nothing because the units sit idle waiting on memory.

Prefill sits on the other side of the roofline. A prefill pass processes p tokens at once, so each weight read is amortized over p tokens. At p = 130,659 the intensity is roughly p FLOPs per byte, hundreds of times above the balance point, and the pass is compute-bound. That is why prefill runs at 39,237 tokens per second while decode runs at 59.1. Same hardware, opposite bottleneck.

Batching is the whole game in serving. Four concurrent streams on this pair produce 106.2 tokens per second aggregate against 59.1 for one, a multiplier of 1.80. Not 4.0. The weight read is shared across the batch, and that sharing is where the gain comes from. Each stream's cache read is separate, and the attention kernel walks rows one at a time. Write the step time as a shared term A plus a per-stream term B times the stream count s. The speedup from one to four streams is 4(A + B) / (A + 4B), and setting that equal to 1.80 gives A = 1.45 B. The shared term is only about one and a half times the per-stream term, so the per-stream work is not negligible.

Four streams at the mean prompt hold 484 MB of cache between them, and a step re-reads all of it, which at 273 GB/s costs about 1.8 ms that weight sharing cannot remove. The rest of the per-stream term is the row-wise attention and sampling work. At longer contexts the cache term grows, and the multiplier falls further below 4.

The engine's prefix cache is the mitigation that costs nothing in quality. A prefix cache matches the beginning of a new request against blocks already in the pool. Each block is hashed together with the hash of the block before it, so a match requires the entire prefix to be identical, not just one block. On a hit the allocator increments the block's reference count and points the new request's block table at the existing physical block. Eviction is least-recently-used among blocks whose reference count has fallen to zero. Over the sample window, 12,285,952 of 12,804,579 prompt tokens looked up were hits, or 95.9%. At the measured prefill rate of 39,237 tokens per second, that removed 12,285,952 / 39,237 = 313 seconds of prefill work. Nothing about the model changed. The same numbers were simply not computed twice.

The remaining cost is structural. The pool is fixed at 262,144 positions and shared, so context becomes a resource to be allocated rather than a property of the model. A stream that reserves 32,768 tokens of reply budget has reserved the cache for them whether or not it uses them, which is why the per-stream ceiling is 32,750 and not 65,536.

The KV cache began as an optimization and became the constraint. Multi-query attention, which Shazeer proposed in 2019, and grouped-query attention, which Ainslie and colleagues published in 2023, both attack the same multiplier in the formula, the number of key-value heads. State-space models such as Mamba (Gu and Dao, 2023) avoid a growing cache altogether, and the architectures that deploy at long context tend to carry some answer to the cache question. Nobody set out to make memory the bottleneck of inference. The field arrived there, then reorganized itself around it.

The cache size formula, with the levers

Two tensors, times layers, times key-value heads, times head dimension, times positions, times bytes per element. Move any lever and watch the total. This is why grouped-query attention exists: reducing the head count is the only factor in the formula that does not hurt quality much.
