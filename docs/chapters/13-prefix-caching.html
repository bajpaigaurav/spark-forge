Why the second request is cheaper

If two requests share a prefix, the keys and values for that prefix are identical, so computing them twice is pure waste.

Assumes 12 · Virtual memory for the KV cache. Terms: prefill · token · KV cache · decode · PagedAttention · prefix caching · continuous batching · throughput

A support bot answers a familiar question. The system prompt is identical to the last call. The user's question differs by a sentence. The engine receives the prompt, tokenizes it, and begins prefill. If it recomputes the system prompt from scratch, it has wasted most of the work. The second request should be cheaper because the keys and values for the shared prefix are already known, but only under conditions the mechanism must make explicit.

When a shared prefix is actually reusable

Start with the condition. In a decoder-only transformer, prefill processes the prompt tokens through every layer. At each layer, each token produces a query, a key, and a value. The key and value for token i depend on tokens 1 through i. Attention is causal, so token i never sees tokens after i. If two requests have the same token sequence up to position i, then the key and value at position i are identical in both requests, layer by layer. The computation is deterministic; there is no randomness in the forward pass. The KV cache stores those tensors so decode can attend to them without recomputing. The same storage can be shared across requests when the prefix matches.

The match is stricter than “same tokens.” With rotary position embeddings, the key at a position depends on the absolute position through the RoPE rotation. The same token sequence at a different absolute position produces different keys. A prefix cache therefore requires the shared prefix to start at the same absolute position, usually position 0, because prompts begin there, and the cache key must include the model weights/version, tokenizer, adapter or LoRA identity, dtype, block size, and starting position or block index. If any of those differ, the cached KV is not valid. A fixed system prompt is not literally free. The engine still pays for hash computation, tree lookup, block-table updates, and reference-count bookkeeping, and the cached blocks must still be resident and not invalidated. It is nearly free in prefill compute only while those conditions hold.

What a PagedAttention block stores

The storage unit is the PagedAttention block. In PagedAttention, the KV cache is divided into fixed-size physical blocks, or pages, in GPU memory. A request’s block table maps each logical block index in its token sequence to a physical block ID. For each layer and each head, the cache stores key and value vectors for every token position in the block. A block is therefore a slice across every layer and every head. For layer l, head h, and offset o inside the block, the cache holds a key vector and a value vector of dimension dhead. A physical block ID refers to the same offset in every layer/head’s K and V arrays. PagedAttention gave the KV cache fixed-size blocks and a block table; prefix caching reuses those blocks across requests by pointing a new request’s block table at the same physical pages and incrementing the blocks’ reference counts.

How block hashes bind a block to its prefix

In block-based prefix caching, the lookup uses fixed-size token blocks and a hash table keyed by block content plus the prefix hash; radix-tree caches such as RadixAttention instead match variable-length token sequences along tree edges Take a block of consecutive tokens. Hash the token IDs in the block together with the hash of the previous block and the cache-key namespace fields above. The previous-block hash binds the block to its prefix, so the same tokens at a different place in a document do not collide. The hash table maps the hash to one or more candidate physical KV blocks; implementations may use a fast non-cryptographic hash such as xxHash or a cryptographic hash such as SHA-256, trading lookup speed against collision resistance.

Because collisions are possible, the cache stores the full token IDs, or a strong fingerprint, for each block and verifies the incoming tokens against the stored tokens before reuse. If the stored tokens differ, the entry is a collision and is skipped; a new entry is inserted. The hash is a lookup accelerator; the tree walk and token verification are the correctness check.

A worked example distinguishes the two cases. Suppose the block size is two tokens. Request A has prefix [A1, A2][B1, B2], and Request B has prefix [C1, C2][B1, B2]. The second block contains the same tokens B1, B2 in both requests, but its hash includes the previous-block hash: h(A1,A2) for A and h(C1,C2) for B. The block hashes differ, so B’s second block is not reused from A. Now suppose Request C has prefix [A1, A2][B1, B2], exactly matching A. Its first block hash matches A’s first block, and its second block hash matches A’s second block, so both blocks are reused.

Separately, if the same tokens B1, B2 appear at position 0 in one prompt and position 4 in another, the chained previous-block hash prevents reuse, because the block is bound to its prefix; if the same tokens appeared at a different position, RoPE and the different preceding context would also make the KV values differ.

Radix-tree lookup and the block-size trade-off

The radix tree stores token sequences as edges, with each node representing a shared prefix. On a new request, the engine computes block hashes incrementally and walks the tree from the root. At each node, it compares the incoming tokens to the child edges. If the tokens match an edge, the walk follows it and reuses the KV blocks along that path. If the tokens match part of an edge, the tree splits the edge at the divergence point: the matched prefix becomes a node, and the unmatched suffix becomes a new edge. If the tokens diverge, the walk stops. The engine computes only the remainder, but “remainder” is block-aligned. KV blocks are fixed-size and atomic; the cache does not reuse a partial block’s KV. If divergence falls inside a block, the entire block containing the divergence is recomputed, even if some of its tokens matched.

If the prompt ends inside a block, that partial block is computed for the request but is not shared as a reusable block. The tree split may happen at token granularity for lookup, but reuse happens only for complete blocks whose hashes and stored tokens match. The new request’s block table is updated accordingly. Matched logical blocks point to existing physical block IDs with incremented reference counts. The remainder gets newly allocated physical blocks, the engine writes their K/V, and the block table entries are appended.

Block size is a trade-off. Larger blocks reduce hash-table entries and block-table metadata, and they reduce lookup overhead at block granularity; they do not reduce token-level radix-tree nodes when the tree splits at token granularity. and they improve contiguous reuse, but a divergence inside a large block wastes more recomputation and makes memory allocation coarser. Smaller blocks reduce wasted recomputation at divergence and allow finer sharing, but they increase metadata, hashing, lookup, and block-table overhead. The right size depends on prompt-length distribution and divergence patterns; a common choice is 16 tokens, but it is not universal.

Eviction, admission, and cache isolation

Eviction is where the design gets subtle. The cache cannot hold every block forever. The engine must evict blocks to admit new requests. The eviction policy is least recently used on blocks, not on requests. Each block has a reference count. A live request holds a reference to every block in its KV. When the request finishes, the engine decrements the counts. Blocks with zero references become eviction candidates. The least recently used zero-reference candidate is evicted first. Shared blocks are counted per block-table reference, not per token: if two requests both hold the same physical block, its reference count is two; when one request finishes, the count drops to one and the block remains.

A concrete refcount/LRU example follows. Request A arrives with system-prompt blocks S1, S2 and unique suffix block UA. S1 and S2 have refcount 1; UA has refcount 1. Request B arrives with the same system prompt and a different suffix UB. The lookup matches S1, S2, so their refcounts become 2, and UB is allocated with refcount 1. Request A finishes: S1, S2 drop to 1, and UA drops to 0, so UA becomes an eviction candidate. Request B finishes: S1, S2 drop to 0 and become candidates. A request-level LRU would have evicted S1, S2 when A finished, destroying the shared prefix while B still needed it. Block-level LRU separates the shared prefix from the unique suffix. The system-prompt blocks stay because they are touched by every request. The unique suffix goes because it is touched once.

The radix tree imposes an order. A child block’s KV is only meaningful with its parent prefix. The cache enforces this by evicting leaves first. A parent block cannot be evicted while a child block is live. The enforcement is mechanical. Eviction considers only zero-reference leaf nodes. If a parent has zero references but a live child, the parent remains. If a parent must be invalidated, its descendants are invalidated first. Concurrency safety requires atomic reference-count updates under a per-block lock or a global cache lock. A lookup that finds a candidate must increment the block’s reference count before attaching it to the request’s block table; eviction checks that the count is zero and that the node is a leaf, and it cannot race with an attach. If admission fails after a partial attach, the engine decrements the counts it incremented.

Admission control reserves blocks before admitting a request. The scheduler estimates the prompt blocks plus the reply budget; if free blocks are insufficient, it evicts zero-reference leaves; if still insufficient, it queues or rejects the request rather than admitting it and later evicting live blocks. Scheduling and batching interact with the cache. A high hit rate reduces the number of prefill tokens in a batch, so the scheduler can batch more requests or admit longer prompts. But cache lookup and block-table updates add CPU overhead, and eviction during scheduling can change the hit estimate. Continuous batching must account for both effects.

Cache invalidation and isolation are part of correctness. When the model, tokenizer, adapter, dtype, block size, or position scheme changes, the cache namespace changes; old entries are not reused and may be cleared. If prompts from different tenants can share a cache, a tenant may infer another tenant’s prompt through hit timing or reuse. Production systems either include a tenant ID in the cache key, isolate caches per tenant, or disable cross-tenant sharing; they also verify stored tokens before reuse and clear a tenant’s entries on deletion.

Measuring token-level hit rate and uncached prefill throughput

The metrics must match the mechanism. The token-level hit rate is cached tokens / queried tokens . The request-level hit rate is requests with at least one cached token / requests . A numeric example follows. Request A has 100 prompt tokens and 90 are cached. Request B has 10 prompt tokens and 0 are cached. The token-level hit rate is 90/110 = 81.8%; the request-level hit rate is 1/2 = 50%. A request with one cached token counts as a request-level hit but saves almost no compute. That is why the useful metric is token-level. It tells what fraction of prompt tokens skipped query-token processing; it is not the fraction of total prefill work removed, since uncached tokens still attend over cached KVs and other overhead remains.

The counters are collected during lookup. For every prompt token considered for prefix matching, increment the query-token counter. For every token whose KV block is reused, increment the hit-token counter. The prefill timer wraps only the prefill kernel. Cached tokens are not processed as queries in the prefill kernel, but their KV blocks are read as attention context when prefilling uncached tokens; prefill time therefore excludes cached-token query computation but not attention over cached KV. so the prefill-time denominator excludes them. Therefore the uncached prefill throughput uses prompt tokens minus cached tokens divided by prefill seconds. The naive ratio of all prompt tokens divided by prefill seconds is an effective throughput that includes cache savings and overstates kernel compute throughput; it does not measure cache lookup For a sample window, take the prompt-token count, the cached-token count, and the prefill kernel time for the uncached tokens.

The uncached throughput is the uncached token count divided by that time. A benchmark that reports prefill throughput without the hit rate is reporting the cache’s effect. The same applies to latency. Time to first token includes lookup, prefill of uncached tokens, and scheduling, so comparisons across engines need the hit rate and the uncached prefill throughput.

The second request is cheaper because the first request paid to build a path in the tree.
