VII. Serving · Chapter 26

Two regimes in one machine

Prefill and decode stress completely different parts of the hardware, which is why a single throughput number for a model is meaningless.

The measurements in this chapter come from a pair of NVIDIA DGX Spark systems with GB10 superchips, running a tensor-parallel inference engine. The engine exposes Prometheus-style counters at /metrics; the latency and throughput aggregates below are scraped from that endpoint on 2026-10-31, over a window of 98 requests. The mean prompt in that window is 130,659 tokens, the mean generation is 607 tokens, and the mean prefill duration is 3.33 seconds. The mean decode duration is 8.38 seconds, and the mean time to first token is 3.46 seconds. The concurrency benchmarks were run separately, after the engine had warmed up, with four prompts of 400 completion tokens each, first sequentially and then concurrently.

A request arrives carrying 130,659 tokens of prompt. The engine answers it in two phases that share a machine and almost nothing else. Prefill takes 3.33 seconds on average and emits no visible text. Decode takes 8.38 seconds and emits 607 tokens. Time the request end to end and you get one number, and that number describes neither phase.

Start with prefill. The prompt is a matrix of activations, N rows by d_model columns, where N is the prompt length. Take one weight matrix in a layer — the attention projections are d_model by d_model, while the MLP up/down projections are d_model by d_ff (typically 4·d_model). Each such matrix computes Y = XW + b. The arithmetic-intensity argument below is per weight element, so it holds whatever the matrix The GPU tiles this matmul into blocks of rows and columns. For each output tile, the kernel loads a block of X and a block of W into shared memory, computes the dot products, and accumulates. The weight block is loaded once and reused for every row of X that falls into the tile's row range. In prefill, N is 130,659, so a weight block is reused across a large number of rows. The cost of fetching the weights from memory is amortized across the whole prompt.

The currency for that trade is arithmetic intensity, measured in floating-point operations per byte of memory traffic. Williams, Waterman, and Patterson formalized it in the roofline model in 2009 ("Roofline: An Insightful Visual Performance Model for Multicore Architectures," Communications of the ACM). Consider a bf16 weight. It occupies two bytes and takes part in two floating-point operations per token that uses it, one multiply and one accumulate. During prefill with N tokens in flight, that weight does 2N operations for the same two bytes, so intensity is N operations per byte. With N at 130,659, every byte hauled from memory feeds about 65,330 multiply-accumulates, i.e. 130,659 FLOPs. The arithmetic units are the constraint and the memory bus has room to spare. Prefill is compute-bound, and on this pair it sustains 39,237 tokens per second, measured as prompt_tokens_total divided by request_prefill_seconds_sum over the 98-request window.

Decode inverts every term. A stream that has already eaten its prompt generates one token at a time, and each token depends on the one before it, so there is no matrix–matrix multiply; the same weight matrix now meets a single row of activations in a matrix–vector product. The same weight matrix now meets a single row of activations. It still has to be read from memory in full, two bytes at a time, and now those two bytes feed exactly one multiply-accumulate. Intensity is one operation per byte. The arithmetic units finish long before the memory system delivers the next weight, so they sit idle. Decode is bandwidth-bound. The unified LPDDR5X pool on the GB10 moves 273 GB/s, shared between CPU and GPU, according to NVIDIA's DGX Spark hardware guide. That is a spec figure; the effective bandwidth achieved by the kernel will be lower. The measured single-stream decode rate is 59.1 tokens per second, from four sequential requests of 400 tokens each, 1,600 tokens in 27.1 seconds. That works out to 16.9 milliseconds per token.

A decode step also reads the KV cache. In every layer, for every stream, the attention block pulls the keys and values of all previous positions. The cost per position per layer is one key vector and one value vector, each with H_kv heads times d_head elements. In bf16 each element is two bytes, so the cost per layer per position is 4 × H_kv × d_head bytes. Sum over L layers and divide by the tensor-parallel rank count R. The config allocates 0.9 GiB per rank for 1,048,576 positions, which works out to 922 bytes per position per rank. That 922 is the measured value of 4 × L × H_kv × d_head / R for this model and sharding; for bf16, the product L × H_kv × d_head / R is 230.5. At a mean prompt length of 130,659 tokens, the KV traffic per rank is 130,659 × 922 = 120.5 MB per generated token. At the 32,750-token per-stream ceiling we will derive later, it is 30.2 MB. The difference is 90.3 MB per token, which at 273 GB/s takes 0.33 milliseconds. That increment is the mechanism behind the familiar complaint that long-context decode gets slower as the conversation goes on. Weight traffic per token is fixed; cache traffic per token grows with context. For a full layer, the intensity is the sum of the FLOPs from the QKV projection, the attention score and value products, the output projection, and the MLP, all multiplied by batch B, divided by the sum of the weight bytes for those matrices, the activation bytes, and the KV bytes. In decode, the KV term grows with context and eventually dominates the denominator, so intensity falls as the conversation lengthens.

Every accelerator has a balance point, the intensity at which a kernel stops waiting on memory and starts waiting on the ALUs. It is the peak floating-point rate divided by achievable bandwidth. Kernels below the line are bandwidth-bound, kernels above it are compute-bound. For a weight-bound matmul, intensity is proportional to batch size: B × (FLOPs per MAC) / (bytes per weight). Under the common fp16 convention of 2 FLOPs per MAC, it equals B ops/byte; with fp8 weights it would be 2B ops/byte, so the balance point is a batch size. We do not have a measured peak FLOP/s for this part in the metrics, so we cannot place the ridge point numerically. But we can see the two regimes in the measured rates. Prefill runs at 39,237 tokens per second and decode at 59.1, a ratio of 664. That gap is consistent with a compute-bound prefill phase and a bandwidth-bound decode phase, but the ratio alone mixes batch-size and workload differences; the intensity argument below is what pins the regime At batch 4, the intensity is 4 operations per byte, far below the ridge point for any modern accelerator, so decode remains on the bandwidth-bound side of the line. The measured 1.80x scaling at concurrency 4 is sublinear; that is consistent with bandwidth-bound decode only if batching overhead or incomplete batching is accounted for, so it does not by itself confirm the regime

Clock speed matters to the compute-bound regime. The observed SM clock under load on this part is 2,197 MHz, read from nvidia-smi clocks.sm on 2026-10-31. The GB10 silicon maximum is 3,003 MHz per NVIDIA's documentation, and the thermal design holds the part well below that ceiling. This is a single sample under load, not a sustained average, and we did not measure junction temperature. Prefill can use those megahertz because it is waiting on the ALUs. Decode is dominated by memory bandwidth, so SM clock is not the main throughput lever, but it still affects the SM-side softmax, normalization, sampling, and scheduling work and can influence decode latency and tail throughput. Memory clock and boost behavior are separate from SM clock; the claim here is about the SM clock, not the memory clock. Anyone tuning SM clocks to improve decode throughput is tuning the wrong phase.

Time to first token tracks prefill, since nothing can be emitted until the prompt has been through every layer. The mean TTFT is 3.46 seconds against a mean prefill duration of 3.33 seconds. The 0.13-second gap is the sum of queueing, cache lookup, and the first decode step; the metrics do not break it down further, but it is small relative to prefill. Shazeer named this problem in 2019 when he proposed multi-query attention ("Fast Transformer Decoding: One Write-Head is All You Need"), writing explicitly that incremental decoding is limited by memory bandwidth rather than by arithmetic. That observation motivates many of the KV-cache compression schemes in this book.

The 3.46-second first token is close to the 3.33 s a 130,659-token prompt would take at 39,237 tokens/s, and a prefix cache explains why it is not larger, and a prefix cache explains part of why. The cache stores the KV state for previously seen token prefixes. On a new request, the scheduler walks the prompt from the start and finds the longest matching prefix. It reuses the stored KV for that prefix and prefills only the remaining tokens. The saving in TTFT is the matched token count divided by the prefill rate. In the sampled window, 12,285,952 of 12,804,579 prompt tokens matched, or 95.9%. At 39,237 tokens per second, that reuse removed 313 seconds of prefill work in aggregate. For a single request, a match of 65,536 tokens saves 65,536 / 39,237 = 1.67 seconds of prefill. The aggregate 313 seconds is the sum of such savings over the window, and the aggregate hit rate is not the per-request hit rate; the 98 requests have different prefix lengths and different match lengths.

Batching behaves differently in the two regimes. Decode gains from more streams because a bandwidth-bound kernel has spare arithmetic capacity. Run four streams together and each weight read serves four tokens instead of one, so intensity rises from one operation per byte to four. If the kernel were perfectly bandwidth-bound and KV traffic did not grow, aggregate throughput would scale by 4x. Measured here, aggregate decode went from 59.1 tokens per second at concurrency one to 106.2 at concurrency four, a factor of 1.80. The same four prompts were fired concurrently, completing 1,600 tokens in 15.1 seconds. The gain is real and it is sublinear. If KV traffic were the only thing preventing linear scaling, the speedup would be 4/(1+3f), where f is the KV share of per-token traffic at concurrency one. Setting that equal to 1.80 gives f = 0.407. So KV traffic would have to be 40.7% of per-token traffic to explain the entire shortfall. The rest comes from the kernel layout. The decode round is pinned at 16 rows, the maximum row width of the pinned kit's kernel. At concurrency 4, only 4 of the 16 rows are active, so the weight fetch is amortized 4x but the kernel's row slots are 25% utilized. The 16-row kernel is a maximum. Reducing the row count to the active row count (four here) would reduce ALU waste without changing the bandwidth-bound behavior; reducing it below the concurrency level would cut weight-fetch amortization and lower throughput. The measured 1.80x is the net of the weight-fetch amortization and the KV traffic that scales with the number of streams.

Prefill gains less from batching than decode does, because it is already compute-bound. Adding a second prompt to a prefill batch raises intensity further, but the ALUs are the constraint, so the two prompts split the same finite compute instead of filling idle capacity. This asymmetry is why mixing prefill work into decode steps is expensive. A long prefill inserted between decode steps stalls every stream in the batch. The engine's pair_stall_ms counter accumulates the time decode steps spend waiting for an in-flight prefill on the paired rank; it stood at 120,000 ms since the engine started. That is a cumulative counter rather than a rate, and without the engine's uptime we cannot express it as a percentage. Continuous batching, taken up in its own chapter, is the scheduler's answer to that tension. The scheduler admits new requests at decode step boundaries and chunks long prefills into pieces that fit between decode steps.

Concurrency also runs into a memory ceiling with nothing to do with arithmetic. The KV pool holds 262,144 positions shared across four streams, so an equal split gives 65,536 positions each. Admission reserves the default 32,768-token reply budget, plus 16 round rows, plus two positions of overhead. The reply budget is the maximum number of tokens the request may generate, reserved up front so the KV cache never needs to evict mid-generation. The 16 round rows are the batch width of the decode kernel, which needs KV slots for each row. The two positions are alignment padding required by the attention kernel The admission check compares prompt_tokens + 32,768 + 16 + 2 against 65,536. What remains is 32,750 tokens of context per stream. A prompt longer than that cannot be admitted at concurrency four no matter how much compute is free. If the pool is full, the scheduler evicts the least recently used prefix cache entries to free KV space, but it cannot evict active streams. Raising the pool to the model's native 1,048,576 positions would lift the per-stream ceiling to 229,358 tokens. The extra KV memory per rank is derived from the config's 0.9 GiB per 1,048,576 positions. Raising the pool from 262,144 to 1,048,576 adds 786,432 positions, which is 0.75 of the full window, so the extra memory is 0.9 × 0.75 = 0.675 GiB, rounded to 0.68 GiB per rank. That is the sort of trade a serving engineer argues about at two in the morning. If MemAvailable drops below the 2.5 GiB memguard floor, memguard kills a rank, so the pool cannot be raised without checking the memory headroom on every rank.

The habit of quoting one tokens-per-second figure for a model is a genuine mistake, and it survives because benchmarks rarely state their concurrency. A number measured at concurrency one describes decode bandwidth. A number measured on a long prompt describes prefill compute. They are not comparable and they do not trade off linearly. The honest report is a curve, with time to first token and inter-token latency plotted separately against concurrency and prompt length. Some systems push the logic further and put prefill and decode on different machines altogether, the argument Splitwise (2024) and DistServe (2024) both made, on the grounds that a compute-bound job and a bandwidth-bound job should not share a scheduler. The gain is independent scaling of each phase on hardware suited to its regime. The cost is the KV transfer between machines. At 130,659 tokens, the KV cache is 120.5 MB per rank, and moving that between machines costs bandwidth and latency that must be weighed against the prefill time it saves. As a rule of thumb, disaggregation struggles when the KV transfer cost exceeds the prefill time saved, or when prompts are short and concurrency is low. But that is not the whole criterion: the decision should be made on end-to-end latency/throughput and pool utilization, and SLO isolation or decode-interference avoidance can still justify disaggregation in those regimes That case has real force and real costs, and the chapter on splitting a model across devices takes it up.
