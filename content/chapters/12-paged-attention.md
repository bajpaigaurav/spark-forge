## Virtual memory for the KV cache

### The worst-case reservation and its arithmetic

Orca, the serving system Yu and colleagues described at OSDI in 2022, made a promise on every request it admitted. The scheduler reserved a contiguous stretch of GPU memory sized for the longest sequence the model could produce, and handed that stretch to the request for its entire life. The reservation happened before the first token existed. Nobody knew how long the answer would be. The engine had little choice. Keys and values accumulate one position per generated token, and a buffer cannot grow in place when the bytes after it belong to another request.

Take a reserving engine. Its KV pool holds 262,144 positions and it admits four streams at a time. The admission rule divides the pool equally, so each stream is entitled to 65,536 positions. From that share it subtracts three config constants. The first is the default reply budget, 32,768 tokens, because the rule reserves room for a reply that names no length. The second is the decode round batch width, 16 rows, the widest row kernel the scheduler can assemble. The third is two positions of slack for the position counter's boundary bookkeeping. 65,536 − 32,768 − 16 − 2 = 32,750. A request is admitted against that ceiling whether or not it intends to use it, and it holds the whole 65,536-position share for as long as it runs.

The model's native window is 1,048,576 positions. A pool of 262,144 positions covers a quarter of it. Raising the pool to the full window would add three quarters of the cache's full size, so the cost scales linearly with positions and nothing else. The per-stream ceiling then becomes 1,048,576 / 4 − 32,768 − 16 − 2 = 229,358 tokens. The ceiling is a function of the pool divided by the number of streams. It has almost nothing to do with what any particular request needs.

Two kinds of waste follow. Internal fragmentation is the gap between what a sequence reserved and what it used. A request that finishes at 100 tokens still held its whole 65,536-position share until it finished, so 65,436 positions sat idle for its whole life. External fragmentation is the gap between buffers. Each sequence needs one contiguous run, so a hole left by a departing request can only be reused by a new request whose worst-case length fits inside it. Large holes are rare, since they require a large request to leave first, and the allocator ends up holding plenty of free memory in pieces too small to admit anything.

Kwon and his coauthors at Berkeley measured the cost in 2023, running against FasterTransformer and Orca. Between 20 and 40 percent of the memory reserved for KV cache actually held token state. The rest was a reservation against a future that mostly did not arrive. Orca had already introduced continuous batching, which admits new requests as old ones finish and raises utilization considerably. Continuous batching fixed *when* memory was allocated. It did not fix *how much*.

### Decode is bandwidth-bound

That distinction matters because decoding is bandwidth-bound. HBM3 on an H100 moves 3,350 GB/s. Every decode step reads the weights once and the KV cache of every active sequence. Write W for the bytes of weights, k for the KV bytes per token per sequence, and n for the batch. A step reads W + nk bytes and cannot finish faster than (W + nk) / 3,350×10⁹ seconds. The weights term is fixed; the cache term scales with n. Adding one more sequence adds k / 3,350×10⁹ seconds to the step and one more share of a weight read you were going to pay for anyway. Memory wasted on reservations is throughput you cannot buy back.

Concurrency behaves the way the bandwidth arithmetic predicts. Four sequential 400-token requests pay four full weight reads, one after another. The same four fired concurrently share a single weight read across the batch, so the step is shorter than four steps would be. The gain is real and sublinear, because each sequence still reads its own cache and the attention kernel walks rows one at a time.

### From page tables to PagedAttention

The fix came from an operating system textbook. In virtual memory a process sees a flat, contiguous address space that has nothing to do with where its bytes live. Physical memory is divided into frames of a fixed size. A per-process page table maps each virtual page number to a physical frame number, and the hardware translates every access, consulting a TLB of recent translations and walking the table only on a miss. Because frames need not be adjacent, allocation means finding any free frame rather than finding a contiguous run, and fragmentation collapses to the unused tail of the last page ([[10-kv-cache]] sizes the buffer this replaces).

PagedAttention, published by Kwon and colleagues at SOSP in October 2023 and shipped as vLLM, applies that arrangement to the KV cache. Physical memory is carved at startup into blocks holding a fixed number of token positions. Each physical block ID indexes the KV storage for those positions across all layers, with one per-layer slice per block, for one sequence. A sequence owns a single block table, an array indexed by logical block number whose entries are physical block numbers Growing a sequence past a block boundary means allocating one more block and writing one more pointer. Nothing is copied, and no contiguity is required. Internal fragmentation is bounded by the unused tail of a single block per sequence.

The kernel that reads this layout works one query at a time. For a query at position p, the logical block is p / B and the offset within it is p mod B. The kernel walks the sequence's logical blocks in order, reads each physical block number from the table, loads that block's K and V, and computes Q·Kᵀ over at most B keys. Softmax has to span blocks, so the kernel carries a running maximum m and a running normalizer l, the online-softmax trick from Milakov and Gimelshein in 2018 and Dao's FlashAttention in 2022. For each block it computes the block's local max, rescales the accumulator by exp(m_old − m_new), adds the block's exponentials, and moves on. The final block is usually partial, so the kernel masks positions past the sequence length before taking the max. Block boundaries never split an attention computation; they only split the loop.

### What the gather costs the kernel

Gathering through a table costs something. Each block is a separate memory transaction, and the table read is a dependent load that must complete before the K/V load can start. A contiguous run lets the prefetcher stream and lets the compiler emit one wide vectorized load; a gather cannot. The first paged kernels paid for this. One rewrite hoisted the block-table read into shared memory once per block per warp instead of once per query. Another double-buffered the next block's K/V while computing the current one, to hide the dependent-load latency. A third replaced a separate tail kernel with in-kernel masking of the partial block. In the reported benchmarks, those changes brought the paged kernel to parity with the contiguous one; parity is workload- and block-size-dependent, and small blocks or high concurrency can still make the dependent block-table gather lose

### Copy-on-write sharing and prefix caching

The block table made sharing cheap. Two sequences that branch from the same prompt have block tables whose entries point at the same physical blocks, and each block carries a reference count. Take a prompt of 100 tokens with 16-position blocks. It occupies seven blocks, six full and one holding four tokens. Sequence A's table reads [7, 12, 3, 19, 22, 8, 41], and every one of those blocks has refcount 1. Fork into A and B, and both tables point at the same seven blocks with refcount 2. B generates token 101, which lands in logical block 6, physical block 41. Its refcount is 2, so the engine takes a free block, say 55, copies 41's contents into it, rewrites B's entry 6 to 55, and decrements 41 to 1. A's table is untouched. The copy is one block, not the prefix. This is `fork()` and copy-on-write, transplanted, and it is what makes parallel sampling and beam search affordable.

The same mechanism extends across requests that were never related. vLLM added automatic prefix caching in 2024. The hash granularity is one block, and each block's hash is chained to the hash of the block before it, so a hash identifies the whole prefix up to that block rather than the block alone. On a hit the engine compares the stored token IDs against the incoming ones before reusing the block, which is how collisions are caught; a 64-bit hash by itself would not be enough. Only full blocks are cached. A partial tail block is never shared, because its contents change as tokens are appended. Eviction is LRU over blocks whose refcount has fallen to zero, and a cached block stays in the hash map until it is evicted or reused, at which point its refcount goes back to 1.

When many requests share a long system prompt or a retrieved document, most of their prompt tokens are served from cache. A hash and a pointer chase replace the forward pass for every block that matches, and the saving grows with how much traffic shares a prefix. The cache does not change the model; it just avoids computing the same numbers twice.

### Admission, block size, and where paging stops paying

Admission in a paged engine looks different from the reserved engine's ceiling. The scheduler admits a request when the free-block count covers the blocks its prompt needs; the next token may fit in the last partial block, and a new block is allocated only if that block is full. It does not reserve the reply budget. If the pool runs dry, the scheduler preempts the lowest-priority sequence, either swapping its blocks to CPU memory or dropping them and recomputing the prefix later. The ceiling becomes the pool itself, and no per-stream division applies.

Block size is the tuning knob, and the trade fits in a short list. Take a 100-token sequence and count the blocks a paged engine allocates:
- Block size 8: 100 / 8 = 12.5, so 13 blocks. Twelve are full and the last holds the remaining 4 tokens, so 4 of tail waste and 13 table entries.
- Block size 16: 100 / 16 = 6.25, so 7 blocks. 7 × 16 = 112 positions, so 112 - 100 = 12 of tail waste, and 7 entries.
- Block size 32: 100 / 32 = 3.125, so 4 blocks. 4 × 32 = 128 positions, so 128 - 100 = 28 of tail waste, and 4 entries.
- Block size 64: 100 / 64 = 1.5625, so 2 blocks. Two blocks cover 128 positions, and 128 - 100 = 28 of tail waste, with 2 entries.

Small blocks cut the tail waste and multiply the table entries the kernel must chase; large blocks do the reverse. Sixteen positions is the common default because it keeps the table small enough to cache and the waste small enough to ignore.

The virtual-memory analogy has limits worth naming. There is no page fault. Blocks come from a pool allocated at startup, and the engine never migrates a block to disk mid-step. There is no TLB. The block table is read from global memory on each kernel launch and cached in shared memory or registers by hand, which is why the hoisting rewrite mattered. And the indirection has a real cost that reservation does not pay. When sequences are short and uniform, reservation waste is small and the gather overhead dominates, so a contiguous allocator can win. Paging pays when lengths vary widely, which is the normal case for chat traffic.

Against FasterTransformer and Orca, the vLLM paper reported two to four times the throughput on the same hardware. Memory capacity bounds the batch size, and in the bandwidth-bound decode regime batch size is the dominant throughput lever — though compute or attention bandwidth can cap it sooner. Paging cuts the waste per sequence from most of a worst-case buffer to at most one block, and a larger batch amortizes each weight read over more tokens.

NVIDIA's TensorRT-LLM ships paged KV blocks, and SGLang's RadixAttention, described by Zheng and colleagues in 2024, manages the KV cache as a radix tree of token prefixes, a different allocation abstraction from vLLM’s fixed-size paged block table, so that shared prefixes are found by tree walk rather than by hash. The idea changed the KV cache from a private buffer into an addressable resource, and once memory is reached through a table, sharing, eviction, offloading and defragmentation become ordinary allocator problems rather than special cases.

A reserving engine still caps what a request can ask for. Its per-stream ceiling sits at 32,750 tokens while the model's window is 1,048,576, and the gap is a line in a config file. Raising the pool lifts the ceiling to 229,358, still well short of the full window, and the pool stops wherever memory runs out. The ceiling moves until it hits that floor. The silicon sits far above it.
