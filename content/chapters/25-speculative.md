## Chapter 25: Guessing ahead and checking cheaply

A decode step on a large model is mostly a memory errand. The engine holds 111.5 GB of weights, caches, and live streams in unified memory (tensorfold:device_memory_bytes from /metrics, 2026-10-31). The memory bus moves 273 GB/s, shared between CPU and GPU (NVIDIA DGX Spark hardware guide, docs.nvidia.com/dgx/dgx-spark/hardware.html). During decode, each layer’s weight matrices (attention projections and MLP matrices) are streamed from that memory and multiplied by one token’s activation vector. A transformer decoder stores, for each past token, a key and value vector per layer. That store is the KV cache. Decode appends one token at a time and reads the whole cache. Prefill processes many prompt tokens at once. Decode processes one token per stream per step unless a kernel packs rows from several streams. A kernel is memory-bound when the bytes it moves per arithmetic operation exceed the machine’s bandwidth-to-compute ratio. It is compute-bound when arithmetic saturates. The SM clock is the streaming multiprocessor clock reported by nvidia-smi. The observed SM clock is 2,197 MHz against a 3,003 MHz silicon ceiling (nvidia-smi clocks.sm, 2026-10-31; GB10 silicon maximum SM clock, NVIDIA DGX Spark documentation). That headroom is consistent with the part not being thermally limited, though a thermal ceiling below the silicon maximum cannot be ruled out from clock readings alone It does not prove the arithmetic units are idle. Single-stream decode runs at 59.1 tokens per second (measured: 4 sequential requests of 400 tokens each, 27.1 s total, 1,600 tokens). At four concurrent streams the aggregate is 106.2 tokens per second (same 4 prompts fired concurrently, 15.1 s wall). The ratio is 1.80 times the single-stream rate (derived: 106.2 / 59.1). That is sublinear scaling. I did not measure bus utilization counters, so I cannot attribute the shortfall to contention. The number stands as measured. Prefill reaches 39,237 tokens per second over 98 sampled requests (derived: prompt_tokens_total / request_prefill_seconds_sum from /metrics). That is evidence the machine can sustain many token rows when rows are batched, though it is not a direct SM occupancy measurement. The pinned kit is the container image and kernel set pinned in scripts/local.sh and the live serve argv. Its decode round batch width is 16 rows (ROUND_ROWS=16), so the kernel packs up to 16 rows per weight load.

Speculative decoding attacks the decode gap. A cheap drafter guesses several tokens ahead. The target model checks all of them in one forward pass. The drafter can be a smaller model from the same family, a set of auxiliary heads, or a separate network trained for the job. It generates k candidate tokens autoregressively with its own weights. The drafter’s own decode is also bandwidth-bound, but its weights are smaller, so it usually runs faster than the target. The target model then runs a forward pass over the prompt plus the k candidates. Because attention is causal, the target’s logits at position i are conditioned on tokens up to and including i; the distribution used to score the draft token at position i is therefore conditioned only on the tokens before i. One pass gives a target distribution for every draft position at once. The target scores candidates. It does not generate them.

A verification pass over k draft tokens is a batched GEMM. The kernel loads each weight matrix once and multiplies it by a k-row activation matrix. Weight traffic is the same as a one-token decode step. Arithmetic grows by roughly k. Attention and KV writes also grow by k. For each draft token, the target computes attention over the prompt and all preceding draft tokens (acceptance is decided after the pass; KV entries for rejected drafts are discarded), then writes a key and value vector per layer. At the sampled mean prompt length of 130,659 tokens (derived: prompt_tokens_total / request count = 12,804,579 / 98), attention over the context is a real term. A k=4 pass does four rows of attention over 130,659 keys per layer plus four KV writes. The wall-clock cost is one weight stream plus that attention and write work. It is about one decode step only when the extra k-row attention and KV-write work is small compared with the weight stream—i.e. when context length is short relative to model size (k·C ≪ parameter count), not merely when k is small relative to context The sampled window has mean prefill duration 3.33 s, mean decode duration 8.38 s, and mean time to first token 3.46 s over 98 requests (derived from /metrics counters). I do not have per-kernel timings in the metrics. The aggregate prefill rate and mean prefill duration are the closest available. A direct kernel timing would settle the constant.

The verifier walks the draft left to right. Let q(x) be the probability the draft assigned to token x, and let p(x) be the probability the target assigns to that same token. The draft samples x from q. The verifier accepts x with probability min(1, p(x)/q(x)). If p is at least q, the token is always accepted. If p is smaller than q, the token is accepted only part of the time, in proportion to how much the target believes in it relative to the draft. When the verifier rejects a token, it samples a replacement from the residual distribution proportional to max(0, p(x) - q(x)). The accepted mass and the residual mass add up to p exactly. Here is the derivation. The accepted branch contributes min(q(x), p(x)). The reject probability is R = Σ_y max(0, q(y) - p(y)). Since Σ p = Σ q = 1, R equals Z = Σ_y max(0, p(y) - q(y)). The reject branch contributes R times the normalized residual, which is max(0, p(x) - q(x)). The sum is min(p(x), q(x)) + max(0, p(x) - q(x)) = p(x). That is the exactness proof for one token.

A numeric example makes the residual sampler concrete. Let the vocabulary have three tokens A, B, C. Let q = (0.5, 0.3, 0.2) and p = (0.2, 0.5, 0.3). The draft samples A with probability 0.5. The target assigns A probability 0.2, so the accept probability is min(1, 0.2/0.5) = 0.4. If the draft samples A and the verifier rejects it, the residual is max(0, p - q) = (0, 0.2, 0.1). The normalizer is Z = 0.3, so the normalized residual is (0, 2/3, 1/3). The verifier samples B with probability 2/3 or C with probability 1/3. The output probabilities are A: 0.5 × 0.4 = 0.2; B: 0.3 × 1 + 0.5 × 0.6 × (2/3) = 0.3 + 0.2 = 0.5; C: 0.2 × 1 + 0.5 × 0.6 × (1/3) = 0.2 + 0.1 = 0.3. The output distribution is p. To implement this, compute p and q over the vocabulary, draw u from Uniform(0,1), accept if u ≤ min(1, p(x)/q(x)); otherwise compute r_i = max(0, p_i - q_i), sum Z, and draw from r/Z.

Temperature and top-p need care. Apply temperature and top-p to p and q before the ratio. The q in the ratio must be the draft’s actual sampling distribution after its own temperature and top-p. Different truncation does not break exactness, provided q is the draft’s actual post-truncation distribution and p is the target’s post-truncation distribution; it only changes the acceptance rate The residual must be over the target’s support. A token that the target’s top-p sets to zero can still appear in the draft, and the verifier will reject it with probability one.

For k > 1, apply the same rule left to right. Conditional on the accepted prefix, the draft’s next-token distribution q_i and the target’s p_i are the distributions at that position. The single-token argument says the next output token is distributed as p_i. If token i is rejected, the procedure samples from the residual and stops. Later draft tokens are discarded because they were conditioned on a token the target would not have produced. If all k pass, the target samples one bonus token from p_{k+1}. By induction on positions, each output token conditional on the prior output is target-distributed. The joint distribution of the output prefix is the target’s autoregressive distribution. This is the theorem in Leviathan et al. “Fast Inference from Transformers via Speculative Decoding,” ICML 2023, and Chen et al. “Accelerating Large Language Model Decoding with Speculative Sampling,” arXiv 2302.01318, 2023. Both prove exactness, not approximation. The target model remains the authority. The drafter only supplies candidates.

The arithmetic of the gain follows from the prefix accounting. If acceptance is independent with probability α, the expected number of output tokens per round is E = 1 + α + α^2 + … + α^k = (1 - α^{k+1}) / (1 - α). Let t_d be draft time per token, t_v verification time for k tokens, and t_t baseline target decode time per token. Round time is k t_d + t_v. Speedup over target decode is E t_t / (k t_d + t_v). Take k = 4, α = 0.7, t_d = 0.2 t_t, and t_v = 1.0 t_t. Then E = 1 + 0.7 + 0.49 + 0.343 + 0.2401 = 2.7731. Round time is 4 × 0.2 t_t + 1.0 t_t = 1.8 t_t. Speedup is 2.7731 / 1.8 = 1.54. A faster drafter with α = 0.3 and t_d = 0.05 t_t gives E = 1 + 0.3 + 0.09 + 0.027 + 0.0081 = 1.4251. Round time is 4 × 0.05 t_t + 1.0 t_t = 1.2 t_t. Speedup is 1.4251 / 1.2 = 1.19. The faster drafter loses to the slower, higher-acceptance drafter. If t_v = 1.2 t_t and α = 0.1, E = 1.1111 and round time is 1.24 t_t, so speedup is 0.896. That drafter loses to no speculation at all. Choose k by this formula. Increase k while α^k remains high and k t_d stays small relative to t_v. If acceptance decays with k, a smaller k wins. Choose the drafter by measured end-to-end speedup on your traffic, since acceptance, draft time, k, and verification time interact; high acceptance is a strong signal but not sufficient by itself A drafter with higher α but slower t_d can win when t_v is large. Measure α on your traffic, not paper numbers.

The phrase “accepts only one token” hides two cases. If the verifier rejects the first draft token, the round outputs one token, the replacement. That round bought one token and paid draft plus verification, so it loses ground. If it accepts the first token and rejects the second, the round outputs two tokens, the accepted first plus the residual second. That round bought two tokens for one verification pass. The accounting is prefix length plus one replacement or bonus.

The verification pass writes KV entries for draft tokens. If token i is rejected, entries for i and later are discarded. The cache truncates to the accepted prefix length. If all k pass, the bonus token is sampled from the final logits, but its KV entry is not written during verification; it must be computed in a later forward pass. The cache after the round holds the accepted draft prefix Tree verification needs branch-aware rollback. Keep the KV entries on the accepted path and free the rest.

Medusa, from Cai et al. “Medusa: Simple LLM Inference Acceleration Framework with Multiple Decoding Heads,” arXiv 2401.10774, 2024, removed the separate draft model. It attaches several decoding heads to the target model’s final hidden state. Each head predicts a token at a different offset. One head predicts the next token, another predicts the token after that, and so on. At inference, the heads produce a tree of candidate continuations. A tree attention mask lets the target model verify all branches in one pass. The heads are trained with cross-entropy against the ground-truth next tokens from the training data, using the frozen target model’s hidden states as input; conditioning on those hidden states lets them approximate the target model’s continuation distribution rather than a separate draft model’s.

A tree example shows the mask. Take a draft tree with root prompt and four draft positions. Position 1 is token A. Position 2 is B, child of A. Position 3 is C, child of A. Position 4 is D, child of the root. The attention mask rows for the four draft positions are row 1: 1 0 0 0; row 2: 1 1 0 0; row 3: 1 0 1 0; row 4: 0 0 0 1. Every row also attends the prompt. Row 2 attends A and B. Row 3 attends A and C. Row 4 attends D only. The mask is a lower-triangular pattern on each branch, with zeros across sibling branches. The kernel computes A once and shares its KV entry between the B and C branches. After verification, if B is accepted and C and D are rejected, the cache keeps prompt, A, B and frees C, D. That is branch dedup plus rollback.

EAGLE, from Li et al. “EAGLE: Speculative Sampling Requires Rethinking Feature Uncertainty,” arXiv 2401.15077, 2024, drafts at the feature level. The draft model takes the target model’s hidden state at position t together with the embedding of the next token, and predicts the hidden state at t+1. The target’s LM head converts that predicted state to a token distribution. Training minimizes a regression loss against the target’s hidden states, with a token-level cross-entropy term. The draft operates in the target’s feature space. A sampled token ID is a single choice from a distribution. The hidden state that produced it contains the context that shaped the choice. Drafting from features gives the drafter a richer signal, and that can raise acceptance. EAGLE’s draft model is still small, but it operates in the target model’s feature space rather than in vocabulary space.

Multi-token prediction trains the capability into the model itself. Gloeckle et al. “Better & Faster Large Language Models via Multi-token Prediction,” arXiv 2404.19737, 2024, showed that auxiliary heads predicting several future tokens improve training. DeepSeek-V3, “DeepSeek-V3 Technical Report,” arXiv 2412.19437, 2024, built multi-token prediction modules into pretraining. With heads at offsets 1, 2, and 3, head 1 predicts token t+1 from hidden state h_t. Head 2 predicts t+2 from h_t and the embedding of t+1. Head 3 predicts t+3 from h_t and the embeddings of t+1 and t+2. The heads share the embedding and output head. Training adds cross-entropy at each offset to the main next-token loss. At inference, those heads draft a chain and the target verifies it. There is no separate small model to train or load. The target model’s own weights produce the draft, and the same weights verify it. Joint training gives the heads the target’s own distribution, which can raise acceptance.

The engine’s DSpark drafter is a multi-token prediction head set. Its counters give an acceptance rate of 67.6%: 42,181 accepted tokens out of 62,390 drafted (derived: mtp_accepted_total / mtp_drafted_total from /metrics). Those counters aggregate since process start. They do not record k, temperature, top-p, dataset, or per-request breakdown. So 67.6% is an operational acceptance rate over mixed traffic, not a controlled benchmark. It is the main input to whether speculation pays on this engine, though the payoff also depends on accepted tokens per verification pass (hence k), draft cost, and batch size, but it cannot be compared to paper numbers without matching settings. A faster drafter that is accepted less often can lose ground, because the target pass is the expensive unit. Draft cost enters the break-even at every acceptance level. The speedup is roughly the accepted tokens per target pass divided by 1 + k·c, where c is the drafter

The next measurement I would want is a per-k verification kernel timing at the sampled context length. Without it, the 67.6% acceptance rate and the 1.80x concurrency ratio are the two numbers that bound what this engine can claim.
