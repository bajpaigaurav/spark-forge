## Two regimes in one machine

A request arrives carrying 100,000 tokens of prompt. The engine answers it in two phases that share a machine and almost nothing else. Prefill runs the whole prompt through every layer and emits no visible text. Decode then emits one token per step, each depending on the one before it. Time the request end to end and you get one number, and that number describes neither phase.

The two phases differ in what limits them. Prefill has many rows of work per weight read and is bound by arithmetic. Decode has one row per weight read and is bound by memory bandwidth. Almost every serving decision follows from that split.

### Prefill is compute-bound

Start with prefill. The prompt is a matrix of activations, N rows by d_model columns, where N is the prompt length. Take one weight matrix in a layer: the attention projections are d_model by d_model, while the MLP up and down projections are d_model by d_ff, typically four times d_model. Each such matrix computes Y = XW + b. The GPU tiles this matmul into blocks of rows and columns. For each output tile, the kernel loads a block of X and a block of W into shared memory, computes the dot products, and accumulates. The weight block is loaded once and reused for every row of X that falls into the tile's row range. In prefill, N is 100,000, so a weight block is reused across a large number of rows. The cost of fetching the weights from memory is amortized across the whole prompt.

The currency for that trade is arithmetic intensity, measured in floating-point operations per byte of memory traffic. Williams, Waterman, and Patterson formalized it in the roofline model in 2009 ("Roofline: An Insightful Visual Performance Model for Multicore Architectures," Communications of the ACM). Consider a bf16 weight. It occupies two bytes and takes part in two floating-point operations per token that uses it, one multiply and one accumulate. During prefill with N tokens in flight, that weight does 2N operations for the same two bytes, so intensity is N operations per byte. With N at 100,000, every byte hauled from memory feeds 100,000 FLOPs. The arithmetic units are the constraint and the memory bus has room to spare. Prefill is compute-bound.

### Decode and the KV cache

Decode inverts every term. A stream that has already eaten its prompt generates one token at a time, and each token depends on the one before it, so there is no matrix–matrix multiply; the same weight matrix now meets a single row of activations in a matrix–vector product. It still has to be read from memory in full, two bytes at a time, and now those two bytes feed exactly one multiply-accumulate. Intensity is one operation per byte. The arithmetic units finish long before the memory system delivers the next weight, so they sit idle. Decode is bandwidth-bound. On an H100, HBM3 moves 3,350 GB/s. A 70B model at four bits reads 35 GB per token, so the floor is 35 GB / 3,350 GB/s = 10.4 ms per token for a single stream. At sixteen bits the same model reads 140 GB per token and the floor becomes 41.8 ms.

A decode step also reads the KV cache. In every layer, for every stream, the attention block pulls the keys and values of all previous positions. The cost per position per layer is one key vector and one value vector, each with H_kv heads times d_head elements. In bf16 each element is two bytes, so the cost per layer per position is 4 × H_kv × d_head bytes. Sum over L layers and divide by the tensor-parallel rank count R.

Take Llama 2 70B: 80 layers, 8 KV heads at 128 dimensions, two bytes per element. Each layer holds 8 × 128 = 1,024 values per position, keys and values across 80 layers come to 2 × 80 × 1,024 = 163,840 values per position, and at two bytes each that is 327,680 bytes per position, a third of a megabyte. A 100,000-token context therefore needs 100,000 × 327,680 = 32,768,000,000 bytes of cache. At the 32,750-token per-stream ceiling derived later, the same cache is 32,750 × 327,680 = 10,731,520,000 bytes. The difference is 32,768,000,000 − 10,731,520,000 = 22,036,480,000 bytes per stream. That increment is the mechanism behind the familiar complaint that long-context decode gets slower as the conversation goes on: the extra cache read per token is comparable to the weight read itself, and it grows with context while the weight read stays fixed.

### The ridge point

Every accelerator has a balance point, the intensity at which a kernel stops waiting on memory and starts waiting on the ALUs. It is the peak floating-point rate divided by achievable bandwidth. On an H100 that is 989 TFLOPS against 3,350 GB/s, or 295 FLOPs per byte. Kernels below the line are bandwidth-bound, kernels above it are compute-bound. For a weight-bound matmul, intensity is proportional to batch size: B × (FLOPs per MAC) / (bytes per weight). Under the common convention of two FLOPs per MAC, it equals B operations per byte; with fp8 weights it would be twice that, so the balance point is a batch size. Here the balance point is roughly 300 rows.

That number tells you where each phase sits. Prefill runs at N rows, and N is 100,000, two orders of magnitude above the ridge, so the arithmetic units bind. Decode at batch one sits at one operation per byte, three hundred times below the ridge, so the memory system binds. Batching moves decode toward the ridge but does not cross it at the batch sizes a server actually runs: at batch 4 the intensity is four operations per byte, still far below 295.

Clock speed matters to the compute-bound regime and barely at all to the bandwidth-bound one. Prefill can use every megahertz because it is waiting on the ALUs. Decode is dominated by memory bandwidth, so SM clock is not the main throughput lever, though it still affects the SM-side softmax, normalization, sampling, and scheduling work and can influence decode latency and tail throughput. Anyone tuning SM clocks to improve decode throughput is tuning the wrong phase.

### Time to first token and prefix reuse

Time to first token tracks prefill, since nothing can be emitted until the prompt has been through every layer. It is prefill plus queueing, a cache lookup, and one decode step. The prefill term dominates whenever the prompt is long, which is why the two numbers usually differ by little. Shazeer named this problem in 2019 when he proposed multi-query attention ("Fast Transformer Decoding: One Write-Head is All You Need"), writing explicitly that incremental decoding is limited by memory bandwidth rather than by arithmetic. That observation motivates many of the KV-cache compression schemes in this book.

A prefix cache cuts the prefill term without changing the model. The cache stores the KV state for previously seen token prefixes. On a new request, the scheduler walks the prompt from the start and finds the longest matching prefix. It reuses the stored KV for that prefix and prefills only the remaining tokens. The saving in time to first token is the matched token count divided by the prefill rate. When many requests share a long system prompt or a retrieved document, most of their prompt tokens match, and the saving is most of the prefill. An aggregate hit rate is not the same as the per-request saving: requests arrive with different prefix lengths and different match lengths, so one number hides a wide spread.

### Batching gains and admission limits

Batching behaves differently in the two regimes. Decode gains from more streams because a bandwidth-bound kernel has spare arithmetic capacity. Run four streams together and each weight read serves four tokens instead of one, so intensity rises from one operation per byte to four. If the kernel were perfectly bandwidth-bound and KV traffic did not grow, aggregate throughput would scale by 4×. It does not, because each stream adds its own cache read to the step. Write f for the KV share of per-token traffic at concurrency one; the speedup ceiling is 4/(1+3f). At f = 0.4 the ceiling is 1.8×, and the shortfall is cache traffic rather than wasted arithmetic. The real figure also carries kernel-layout costs: a decode kernel that packs rows wide amortizes each weight fetch across the batch, but its row slots go idle when the batch is smaller than the slot count.

Prefill gains less from batching than decode does, because it is already compute-bound. Adding a second prompt to a prefill batch raises intensity further, but the ALUs are the constraint, so the two prompts split the same finite compute instead of filling idle capacity. This asymmetry is why mixing prefill work into decode steps is expensive. A long prefill inserted between decode steps stalls every stream in the batch. Continuous batching, taken up in its own chapter, is the scheduler's answer to that tension. The scheduler admits new requests at decode step boundaries and chunks long prefills into pieces that fit between decode steps.

Concurrency also runs into a memory ceiling with nothing to do with arithmetic. The KV pool holds 262,144 positions shared across four streams, so an equal split gives 65,536 positions each. Admission reserves the default 32,768-token reply budget, plus 16 round rows, plus two positions of overhead. The reply budget is the maximum number of tokens the request may generate, reserved up front so the KV cache never needs to evict mid-generation. The 16 round rows are the batch width of the decode kernel, which needs KV slots for each row. The two positions are alignment padding required by the attention kernel. The admission check compares prompt_tokens + 32,768 + 16 + 2 against 65,536. What remains is 32,750 tokens of context per stream. A prompt longer than that cannot be admitted at concurrency four no matter how much compute is free. If the pool is full, the scheduler evicts the least recently used prefix cache entries to free KV space, but it cannot evict active streams. Raising the pool to the model's native 1,048,576 positions would lift the per-stream ceiling to 229,358 tokens, and the cache would grow in proportion to the positions it stores.

### Why one tokens-per-second number misleads

The habit of quoting one tokens-per-second figure for a model is a genuine mistake, and it survives because benchmarks rarely state their concurrency. A number measured at concurrency one describes decode bandwidth. A number measured on a long prompt describes prefill compute. They are not comparable and they do not trade off linearly. The honest report is a curve, with time to first token and inter-token latency plotted separately against concurrency and prompt length. Some systems push the logic further and put prefill and decode on different machines altogether, the argument Splitwise (2024) and DistServe (2024) both made, on the grounds that a compute-bound job and a bandwidth-bound job should not share a scheduler. The gain is independent scaling of each phase on hardware suited to its regime. The cost is the KV transfer between machines: at a 100,000-token context the cache is tens of gigabytes per stream, and moving that costs bandwidth and latency that must be weighed against the prefill time it saves. As a rule of thumb, disaggregation struggles when the KV transfer cost exceeds the prefill time saved, or when prompts are short and concurrency is low. But that is not the whole criterion: the decision should be made on end-to-end latency and throughput and on pool use, and SLO isolation or decode-interference avoidance can still justify disaggregation in those regimes. That case has real force and real costs, and the chapter on splitting a model across devices takes it up.
