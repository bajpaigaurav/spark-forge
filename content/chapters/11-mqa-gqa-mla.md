## Chapter 11: Three generations of sharing the cache

### Why the KV cache exists

A decoder at step *t* has already emitted *t*−1 tokens, and to emit the next one it needs to attend over all of them. For each head, the model computes a score between the new query and each previous key. The score is *q*·*k* / sqrt(*d*_head). It masks positions after *t*−1 by setting their scores to negative infinity, applies softmax over the allowed positions, and uses the resulting weights to average the previous value vectors. The keys and values were computed on earlier steps and do not change, so recomputing them wastes work. Every serving stack stores them as the KV cache.

### The arithmetic behind the cache bill

The cache size per token is `2 × layers × kv_heads × d_head × dtype_bytes`. The factor 2 is for one key vector and one value vector. `kv_heads` is the number of key-value heads, which equals the query head count in multi-head attention and can be smaller in the sharing schemes below. Take a representative model with 32 layers, 32 query heads, *d*_head=128, stored in FP16 at 2 bytes. Multi-head attention caches 2 × 32 × 32 × 128 × 2 = 524,288 bytes per token, or 512 KiB. At 4,096 tokens that is 2 GiB. MQA with one KV head caches 2 × 32 × 1 × 128 × 2 = 16,384 bytes per token, or 16 KiB, and 64 MiB at 4,096 tokens. The ratio is 32x.

On the machine this book measures, the shared pool holds 262,144 positions split across 4 request slots. That is 65,536 positions per stream before admission overhead. Admission reserves the 32,768-token reply budget, 16 round rows, and 2 overhead positions, leaving 32,750 tokens per stream. The pool is a reserved block, not a paged allocator; each stream gets a fixed slice. Raising the pool to 1,048,576 positions adds 786,432 positions. The configuration script budgets 0.9 GiB per rank for 1,048,576 positions, so the extra is 0.9 × 786,432 / 1,048,576 = 0.675 GiB, rounded to 0.68 GiB per rank. That is the shape of the problem: context is a knob you pay for in gigabytes, linearly, forever.

### From multi-head to multi-query attention

The original transformer did not treat this as a problem, because it was not built for serving. Vaswani and colleagues, in "Attention Is All You Need" (2017), split the model dimension into several heads, and gave each head its own query, key and value projections. The reason is structural. A head learns what to look for and what to advertise as worth looking for, and those two learned subspaces are coupled. If head three wants to find previously-mentioned dates and head five wants to find syntactic heads of phrases, they need different key spaces to express that. Multi-head attention buys expressiveness by giving every head a private key-value vocabulary, and the cache bill for that expressiveness is one key-value pair per head per token per layer.

Noam Shazeer looked at that bill in 2019 and asked what would happen if all the query heads read from a single shared key head and a single shared value head. His paper is called "Fast Transformer Decoding: One Write-Head is All You Need," and the title is the argument. The key and value projections are the write side of attention; the queries are the read side. Sharing the write side collapses the cache by a factor equal to the number of query heads. The attention score and value-aggregation FLOPs per token do not change, though the K/V projection FLOPs fall; the bytes read from the cache fall For the representative model, MHA reads 16,384 bytes per token per layer from the KV cache; MQA reads 512 bytes. The attention arithmetic intensity rises from 1 FLOP/byte to 32 FLOP/byte. The ridge point is peak FLOPs divided by memory bandwidth. Above it a kernel is compute-bound; below it, bandwidth-bound. That intensity is still below the ridge point for this class of GPU, so the kernel remains bandwidth-bound. Shazeer reported comparable BLEU on WMT14 English-German. The quality cost is real. With one shared key head, every query head retrieves through the same subspace. Chowdhery et al. (2022) reported that MQA training became unstable at PaLM's 540B scale and used query-key layer normalization to stabilize it. Falcon shipped MQA in 2023.

### GQA as a dial and an uptraining recipe

Grouped-query attention arrived in 2023 as the obvious interpolation. Joshua Ainslie and colleagues at Google, in "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints," proposed dividing the query heads into *G* groups, with one key-value head per group. Set *G* equal to the head count and you have multi-head attention back. Set *G* to one and you have multi-query attention. Everything between is a dial. For the representative model with 32 query heads and 8 groups, `kv_heads`=8. The cache per token is 2 × 32 × 8 × 128 × 2 = 131,072 bytes, or 128 KiB, one quarter of MHA. At 4,096 tokens that is 512 MiB.

What made GQA spread was not the dial. It was the uptraining recipe. Ainslie's group showed that you can convert an existing multi-head checkpoint without pretraining from scratch. Within each group, mean-pool the key and value projection matrices across the query heads that will now share them, then continue pretraining for 5% of the original token budget. If original pretraining used *D* tokens, uptraining uses 0.05*D* tokens. With the standard 6*ND* FLOP approximation, uptraining costs 6 × *N* × 0.05*D* = 0.3*ND* FLOPs. The average is a warm start; continued pretraining adapts the shared projection to all its members. Ainslie et al. compared GQA with 1, 2, 4, and 8 groups and found 8 groups close to MHA on their summarization and translation benchmarks. Llama 2 70B uses 8 KV heads for 64 query heads; Mistral 7B uses 8 KV heads for 32 query heads. That adoption followed from kernel support and checkpoint conversion.

### MLA compresses keys and values into a latent

DeepSeek went further in 2024. DeepSeek-V2 introduced multi-head latent attention, and the mechanism is genuinely different from head-sharing. Instead of giving groups of heads a shared key-value head, MLA compresses keys and values into a low-rank latent vector. A down-projection maps the model dimension into a much smaller latent dimension; two up-projections map the latent back out into per-head keys and per-head values. What you cache is the latent plus a separate rotary key, one small vector per token per layer, shared implicitly by every head because every head reconstructs its own key and value from it.

Take a model with 32 layers, 32 heads, *d*_head=128, *d*_model=4096, latent rank 512, and a shared rotary key dimension 64. The cache per token per layer is 512 + 64 = 576 elements. In FP16 that is 1,152 bytes, or 1.125 KiB per token per layer. Across 32 layers that is 36 KiB per token, and 144 MiB at 4,096 tokens. MHA for the same model is 512 KiB per token and 2 GiB at 4,096 tokens. MLA is about 14.2x smaller

### Absorbing projections and decoupling RoPE

The score between query *q* and key *k* is *q*ᵀ*W*_UK*c*, where *c* is the latent and *W*_UK is the up-projection. That equals (*W*_UKᵀ*q*)ᵀ*c*, so the up-projection can be folded into the query projection at load time. The same trick works on the output side: the weighted sum over values is *W*_UV* times the weighted sum over latents, so *W*_UV folds into the output projection. At decode, the kernel multiplies the absorbed query against *c* and adds the rotary part. The full key and value matrices are not materialized. Rotary position embedding, RoPE, rotates queries and keys by position-dependent angles. A rotated key cannot be recovered from a shared latent by any fixed linear map applied to the query, because the rotation depends on where the key sits. DeepSeek's fix was to decouple the rotary key. The cache carries a separate small shared rotary key, one per token rather than per head, that receives RoPE, and the kernel concatenates it with the content part at score time. The cache therefore holds the latent plus that rotary key, which is still far smaller than a full per-head key and value pair.

### The quality-versus-cache curve and adoption constraints

Across the three generations the quality-versus-cache curve has a consistent shape. Multi-query attention sits at the cheap end and pays for it. Grouped-query attention recovers most of the lost quality as soon as you have more than a couple of groups; Ainslie et al. found that 8 groups closely match MHA, so additional groups are generally unnecessary. MLA sits at the far end. Its latent is a learned compression, so each head can reconstruct a distinct key subspace from the shared latent. DeepSeek-V2's report compared against dense models on MMLU, GSM8K, and HumanEval and reported higher MMLU and HumanEval scores but a lower GSM8K score than DeepSeek 67B while shrinking the cache substantially.

Which one you should use depends on what you are allowed to change. GQA is a drop-in: existing kernels handle it, existing checkpoints can be uptrained into it, and the code change is a reshape. MLA is better on the curve, but it is not a drop-in: adopting it requires either training with MLA or uptraining/converting an existing model, plus kernels written and validated for the absorbed-projection form. DeepSeek was building its own stack and could pay that cost. Most of the field could not, so GQA became the default. That outcome follows from engineering constraints rather than a pure quality ranking.

None of these techniques remove the cache. They shrink the per-token cost, and then long context and high concurrency eat the savings back. You still have to decide where each request's cache lives, how much to reserve for it, and what to do when the pool fills. That is an allocation problem, and it is the subject of the next chapter.
