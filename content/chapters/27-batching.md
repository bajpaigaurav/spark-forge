## 27. Continuous Batching and the Scheduler

Four requests arrive within a few milliseconds of one another. The naive move packs their prompts into one tensor, pads the short prompts up to the longest, and decodes until every sequence has emitted its last token. Call that static batching. It wastes the machine twice.

Padding wastes prefill. A batch whose longest prompt runs to 130,659 tokens forces every shorter prompt out to that length, and the attention and feed-forward layers chew through the padding as if it were text. Decode wastes more. Sequences finish at different times. When one request stops after 607 tokens and its neighbour keeps going, the finished sequence still holds a row, still has its KV cache read on every step, and emits nothing. The batch runs at the speed of its slowest member.

A word on what a decode step costs, since everything below depends on it. A transformer layer projects each token into queries, keys, and values, attends over the keys and values of all previous tokens, and writes the new key and value into a cache. Generating token n+1 reuses the cache from tokens 1 through n, so the step reads the whole cache plus the weights and does one token's worth of arithmetic. That ratio of bytes read to FLOPs separates decode from prefill.

Gyeong-In Yu and colleagues at Seoul National University named the fix at OSDI in 2022. Orca introduced iteration-level scheduling, which rebuilds the batch at every decode step. At step t the scheduler holds a set of active sequences, picks a subset that fits the memory budget, runs one forward pass, samples one token per sequence, appends it, and retires anything that emitted an end-of-sequence token or hit its length budget. New requests fill the slots the retirements freed. The batch dimension changes every step. A request can join at step 40 and leave at step 41; another can hold a slot from step 41 to step 900.

That requires attention to stop being one dense matrix multiply. Sequences in a batch sit at different positions and carry different masks. Orca's answer, selective batching, splits the work by operator. The linear projections are position-independent, so every row in the batch goes through one batched matmul. Attention needs per-sequence work. Each query must see only the keys and values of its own sequence, so the kernel segments the batch. It packs the token rows into one buffer, carries a per-token position id so rotary embeddings land at the right offset, and builds a block-diagonal mask that zeroes out cross-sequence attention. In practice the kernel either launches one attention call per sequence and concatenates the outputs, or runs a single fused kernel that reads a per-sequence block table and a per-sequence query range. Either way the projections batch and the attention does not.

Orca left the second problem alone. A new request arrives with a long prompt, and prefill for that prompt is one lump of compute. At 39,237 tokens per second of prefill throughput, a fully uncached 130,659-token prompt occupies the machine for 3.33 seconds, and every decode in flight waits behind it. Sarathi-Serve, published by Amey Agrawal and colleagues in 2024, split prompts into chunks and interleaved those chunks with decode steps.

The justification is a roofline argument, and it is worth doing the arithmetic. For a decode step at batch size B, the machine reads roughly the weight bytes and performs about 2NB FLOPs, where N is the parameter count. Arithmetic intensity is 16B/p FLOPs per byte for p-bit weights. For 16-bit and 8-bit weights that is B to 2B; 4-bit weights give 4B and fp32 gives 0.5B. At B = 4, the 16/8-bit range is 4 to 8 For a prefill chunk of L tokens, intensity is about 2L/w, where w is bytes per weight; with fp16 weights a 2,048-token chunk is about 2,048 FLOP/byte (4,096 only for 1-byte weights) The machine's ridge point, where compute and bandwidth take the same time, falls between those figures, and the measured step times confirm which side each one lands on. Decode at concurrency 4 took 37.7 ms per step against 16.9 ms at concurrency 1, a 2.2x rise for 4x the tokens, which is the signature of a bandwidth-bound step amortizing a fixed weight read. Prefill scales with compute. That gap is what chunked prefill exploits. The chunk's FLOPs ride on arithmetic units that decode leaves idle, and the weights are already resident.

The memory hierarchy matters here. The SMs have small SRAM caches; the 273 GB/s LPDDR5X pool is the next level down and holds the weights and KV. Every byte that misses SRAM costs a trip to that shared pool.

When does the trick fail? When the chunk grows large enough that its compute time stops hiding under the decode step. The measured numbers give the condition. At concurrency 4 the engine sustains 106.2 tokens per second across four streams, so each step emits four tokens and takes 4 / 106.2 = 37.7 ms. A 512-token chunk costs 512 / 39,237 = 13.0 ms of prefill compute, roughly a third of that step, so it lengthens the step by a noticeable margin. A 128-token chunk costs 3.3 ms, under a tenth. The scheduler's per-step prefill cap is the knob. With a cap of C tokens, a prompt of length L takes ceil(L / C) iterations to prefill, and any decode sharing those iterations waits at most C / 39,237 seconds of extra compute per step. For the 130,659-token mean prompt, C = 128 means 1,021 iterations and 3.3 ms of added latency each; C = 512 means 256 iterations and 13.0 ms each. Small chunks buy smoothness and pay in iteration count.

Every iteration runs the same five phases. First, retirement. Sequences that emitted an end-of-sequence token or hit their budget release their KV blocks and their stream slot. Second, admission. The scheduler walks the queue in arrival order, tests each candidate against the memory budget, and admits the ones that fit. Third, preemption. If a high-priority arrival cannot fit, the scheduler picks a resident sequence, usually the newest or the one with the largest KV footprint, and either swaps its blocks out or drops them for recompute. Fourth, the prefill cap. The scheduler takes at most C uncached prompt tokens from the admitted requests. Fifth, the forward pass. Decode rows and the prefill chunk go through one batched call.

The memory test is where the arithmetic lives. On the engine this book measures, the KV pool holds 262,144 positions shared across 4 concurrent streams. An equal split gives each stream 65,536 positions. Admission then reserves the default reply budget of 32,768 tokens, rounds the batch width up to the decode kernel's 16-row granularity, and adds 2 boundary tokens. The arithmetic is 65,536 − 32,768 − 16 − 2 = 32,750 positions per stream. That is the context ceiling a request sees.

The model's native window is 1,048,576 positions, so the pool is a deliberate slice of the 111.5 GB of unified memory that also holds weights and live streams. The memguard process in the live configuration kills a rank when MemAvailable falls below 2.5 GiB, the floor that keeps the pool from crowding out everything else. Raising the pool to 1,048,576 costs 0.68 GiB per rank. That works out to 0.68 × 1,073,741,824 / 1,048,576 = 696 bytes per position per rank. The ceiling arithmetic then runs 1,048,576 / 16 = 65,536, minus 32,768 = 32,768, minus 16 = 32,752, minus 2 = 32,750 positions per stream. So 32,750 reflects the policy choice to divide the pool across 16 streams and reserve the full default reply budget for each The scheduler divides the pool equally and reserves the full default reply budget for every stream, whether or not the stream will use it.

When the pool fills, the scheduler has three options. It can refuse the arrival and leave it queued. It can swap a resident sequence's blocks to another region of memory and read them back later. Or it can drop the blocks and recompute the prefill when the sequence returns. The costs differ by orders of magnitude. A 32,750-position sequence at 696 bytes per position occupies about 22.8 MB. Copying that out and back moves about 4 × 22.8 MB ≈ 91 MB, which at 273 GB/s takes ≈334 microseconds (and more at sustained/contended bandwidth). Recomputing the same sequence at 39,237 tokens per second takes 0.835 seconds. Swap wins by a factor of five thousand for long sequences, which is why the allocator matters as much as the policy.

vLLM's PagedAttention, published by Woosuk Kwon and colleagues in 2023, gave the allocator page-sized blocks, 16 tokens by default, so a sequence's cache can be non-contiguous and reclaimed incrementally. The fragmentation cost is bounded. A sequence wastes at most one partial block, 15 tokens × 696 bytes ≈ 10 KiB, against a contiguous allocator that reserves the maximum length up front and wastes the difference between reservation and use. That difference, for a request that declares 32,768 tokens and generates 607, is most of a 32,750-position per-stream slice.

Fairness is the second decision. First-come-first-served is simple and predictable, but a long generation can occupy a batch slot for a long time and, once the batch is full, delay every arrival behind it Shortest-remaining-first lowers mean latency, and it can starve. Work an example. Suppose a long request has 600 tokens left and each decode step takes 37.7 ms at concurrency 4, so the long request needs about 22.6 seconds of service. Now a stream of 10-token requests arrives every 0.05 seconds. Each short request takes 10 / 26.5 = 0.377 seconds of stream time, so the arrival rate exceeds the service rate and the queue never drains. The long request waits forever. A per-step prefill cap bounds the damage in the other direction, because no single admission can add more than C / 39,237 seconds to a step, and a scheduler that also ages queued requests eventually runs the long one.

Prefix caching changes the scheduler's workload before the scheduler sees it. The engine matches a new prompt against blocks already resident in the pool. A hit means the KV for that prefix is already computed, so the prefill job shrinks from L tokens to L minus the matched length. The projections and attention for those p tokens are skipped, their KV blocks are reused in place, and the kernel starts at position p to compute only the suffix. Attention for the suffix reads the cached prefix blocks alongside the new ones. Over the sampled window, prefix_cache_hits_total / prefix_cache_queries_total = 12,285,952 / 12,804,579 = 95.9%. Prefilling all 12,804,579 prompt tokens at 39,237 tokens per second would take 326 seconds. The 518,627 uncached tokens take 13.2 seconds. The difference, 313 seconds, is the prefill compute the cache removed, and it counts as wall-clock savings only when the machine would otherwise have been busy with that work.

The throughput payoff is real and bounded. Four prompts of 400 tokens each, 1,600 tokens total, run one after another took 27.1 seconds; fired together they took 15.1 seconds. Aggregate decode sums the tokens per second across all active streams, and the recorded rates are 59.1 and 106.2 tokens per second, so 106.2 / 59.1 = 1.80. The mechanism shows up per step. At concurrency 1, a step emits one token and takes 1 / 59.1 = 16.9 ms. At concurrency 4, a step emits four tokens and takes 37.7 ms, so each stream gets 26.5 tokens per second while the aggregate nearly doubles. The step time grew by 2.2x for 4x the KV traffic, so the fixed weight read is being amortized without disappearing.

Admitting one more stream costs almost nothing until the 16-row width fills. The kernel launches in the same shape whether it holds 4 rows or 16, and the 12 padding rows at concurrency 4 consume registers and issue slots but no KV bytes, so the step time does not grow in proportion to the row count. Past 16 rows the kernel runs a second wave, and each wave re-reads the weights, so the step time roughly doubles. What grows before that point is KV traffic, because every step reads the cache of every resident sequence, and those reads all come out of the same 273 GB/s. Continuous batching recovers the waste static batching creates. It does not manufacture bandwidth.

The metrics behind these numbers need definitions. Time to first token is measured from request arrival to the first sampled token, averaged over 98 requests at 3.46 seconds. Decode duration, measured from the first token to the last, averages 8.38 seconds over the same 98 requests. Mean prompt length is prompt_tokens_total / request count = 12,804,579 / 98 = 130,659 tokens, and mean generation is 59,476 / 98 = 607 tokens. All of these come from the engine's Prometheus counters over one window, so they describe one workload and should not be generalized without saying so.

My view is that continuous batching is the most consequential serving idea of the last several years, and it lives in the scheduler. Orca's contribution was noticing that the batch is a queue. The part I would argue with is the equal-split reservation. Reserving 32,768 tokens of reply budget for every stream at admission is simple, and it throws away capacity when requests are short, since the window averages 607 generated tokens per request. A scheduler that sized each reservation to the request's declared budget and rebalanced as sequences retired would fit more streams into the same 262,144 positions. This engine chose predictability, and the cost of that choice is measurable in the gap between 32,768 reserved positions and the 607 tokens a typical request actually uses.
