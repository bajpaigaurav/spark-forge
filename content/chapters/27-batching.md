## 27. Continuous Batching and the Scheduler

Four requests arrive within a few milliseconds of one another. The naive move packs their prompts into one tensor, pads the short prompts up to the longest, and decodes until every sequence has emitted its last token. Call that static batching. It wastes the machine twice.

Padding wastes prefill. A batch whose longest prompt runs to 100,000 tokens forces every shorter prompt out to that length, and the attention and feed-forward layers chew through the padding as if it were text. Decode wastes more. Sequences finish at different times. When one request stops after 200 tokens and its neighbour keeps going, the finished sequence still holds a row, still has its KV cache read on every step, and emits nothing. The batch runs at the speed of its slowest member.

### What a decode step costs

A word on what a decode step costs, since everything below depends on it. A transformer layer projects each token into queries, keys, and values, attends over the keys and values of all previous tokens, and writes the new key and value into a cache. Generating token n+1 reuses the cache from tokens 1 through n, so the step reads the whole cache plus the weights and does one token's worth of arithmetic. That ratio of bytes read to FLOPs separates decode from prefill. On an H100 the balance point is 295 FLOPs per byte; a decode step at batch one sits near one FLOP per byte, so the memory bus is the constraint and the arithmetic units wait. A 70B model at four bits reads 35 GB of weights per token, which at 3,350 GB/s sets a floor of 10.4 ms per token. The cache read is on top of that. Llama 2 70B has 80 layers with 8 KV heads at 128 dimensions, so each layer holds 8 × 128 = 1,024 values per position, and keys and values across all layers come to 2 × 80 × 1,024 = 163,840 values per position. At two bytes each that is 327,680 bytes per position.

### Iteration-level scheduling and selective batching

Gyeong-In Yu and colleagues at Seoul National University named the fix at OSDI in 2022. Orca introduced iteration-level scheduling, which rebuilds the batch at every decode step. At step t the scheduler holds a set of active sequences, picks a subset that fits the memory budget, runs one forward pass, samples one token per sequence, appends it, and retires anything that emitted an end-of-sequence token or hit its length budget. New requests fill the slots the retirements freed. The batch dimension changes every step. A request can join at step 40 and leave at step 41; another can hold a slot from step 41 to step 900.

That requires attention to stop being one dense matrix multiply. Sequences in a batch sit at different positions and carry different masks. Orca's answer, selective batching, splits the work by operator. The linear projections are position-independent, so every row in the batch goes through one batched matmul. Attention needs per-sequence work. Each query must see only the keys and values of its own sequence, so the kernel segments the batch. It packs the token rows into one buffer, carries a per-token position id so rotary embeddings land at the right offset, and builds a block-diagonal mask that zeroes out cross-sequence attention. In practice the kernel either launches one attention call per sequence and concatenates the outputs, or runs a single fused kernel that reads a per-sequence block table and a per-sequence query range. Either way the projections batch and the attention does not.

### Chunked prefill and the roofline

Orca left the second problem alone. A new request arrives with a long prompt, and prefill for that prompt is one lump of compute. A fully uncached 100,000-token prompt occupies the machine for as long as its prefill takes, and every decode in flight waits behind it. Sarathi-Serve, published by Amey Agrawal and colleagues in 2024, split prompts into chunks and interleaved those chunks with decode steps.

The justification is a [[29-roofline|roofline]] argument, and the arithmetic is short. For a decode step at batch size B, the machine reads roughly the weight bytes and performs about 2NB FLOPs, where N is the parameter count. Arithmetic intensity is 16B/p FLOPs per byte for p-bit weights. For 16-bit and 8-bit weights that is B to 2B; 4-bit weights give 4B and fp32 gives 0.5B. At B = 4, the 16- and 8-bit range is 4 to 8 FLOPs per byte. For a prefill chunk of L tokens, intensity is about 2L/w, where w is bytes per weight; with fp16 weights a 2,048-token chunk is about 2,048 FLOPs per byte, and 4,096 only for one-byte weights. The machine's ridge point, where compute and bandwidth take the same time, falls between those figures: 295 FLOPs per byte on an H100. Decode at batch 4 is two orders of magnitude below the ridge; a 2,048-token prefill chunk is above it. That gap is what chunked prefill exploits. The chunk's FLOPs ride on arithmetic units that decode leaves idle, and the weights are already resident.

The memory hierarchy matters here. The SMs have small SRAM caches, the HBM stack is the next level down and holds the weights and KV, and every byte that misses SRAM costs a trip to that larger pool.

When does the trick fail? When the chunk grows large enough that its compute time stops hiding under the decode step. Decode at batch 4 reads four caches instead of one, so its step is longer than the single-stream floor of 10.4 ms but nowhere near four times that, because the weight read is shared. Write f for the KV share of per-token traffic at batch one; the speedup ceiling is 4/(1+3f), and at f = 0.4 that is 1.8×. A chunk of 512 tokens at the ridge is a serious fraction of such a step, so it lengthens the step by a visible margin. A chunk of 128 tokens is a tenth of that. The scheduler's per-step prefill cap is the knob. With a cap of C tokens, a prompt of length L takes ceil(L / C) iterations to prefill, and any decode sharing those iterations waits at most C tokens of extra compute per step. For the 100,000-token prompt, C = 128 means 782 iterations and C = 512 means 196 iterations. Small chunks buy smoothness and pay in iteration count.

### The scheduler's phases and admission arithmetic

Every iteration runs the same five phases. First, retirement. Sequences that emitted an end-of-sequence token or hit their budget release their KV blocks and their stream slot. Second, admission. The scheduler walks the queue in arrival order, tests each candidate against the memory budget, and admits the ones that fit. Third, preemption. If a high-priority arrival cannot fit, the scheduler picks a resident sequence, usually the newest or the one with the largest KV footprint, and either swaps its blocks out or drops them for recompute. Fourth, the prefill cap. The scheduler takes at most C uncached prompt tokens from the admitted requests. Fifth, the forward pass. Decode rows and the prefill chunk go through one batched call.

The memory test is where the arithmetic lives. A KV pool of 262,144 positions shared across four concurrent streams gives each stream 65,536 positions. Admission then reserves the default reply budget of 32,768 tokens, rounds the batch width up to the decode kernel's 16-row granularity, and adds two boundary tokens. The arithmetic is 65,536 − 32,768 − 16 − 2 = 32,750 positions per stream. That is the context ceiling a request sees.

The model's native window is 1,048,576 positions, so the pool is a deliberate slice of the memory that also holds weights and live streams. Raising the pool to the full window multiplies the cache cost by four, since the pool covers a quarter of the window at 262,144 positions. The ceiling arithmetic would then run 1,048,576 / 4 = 262,144, minus 32,768 = 229,376, minus 16 = 229,360, minus 2 = 229,358 positions per stream. The scheduler divides the pool equally and reserves the full default reply budget for every stream, whether or not the stream will use it.

### Eviction and fairness

When the pool fills, the scheduler has three options. It can refuse the arrival and leave it queued. It can swap a resident sequence's blocks to another region of memory and read them back later. Or it can drop the blocks and recompute the prefill when the sequence returns. The costs differ by orders of magnitude. Take a 32,750-position sequence on Llama 2 70B, whose cache is 327,680 bytes per position: the sequence holds 32,750 × 327,680 = 10,731,520,000 bytes of KV. Copying that out and back moves twice those bytes, which at 3,350 GB/s is well under a second. Recomputing the same sequence means running every weight matrix over 32,750 rows, which is orders of magnitude more work than moving the bytes. Swap wins, which is why the allocator matters as much as the policy.

vLLM's PagedAttention, published by Woosuk Kwon and colleagues in 2023, gave the allocator page-sized blocks, 16 tokens by default, so a sequence's cache can be non-contiguous and reclaimed incrementally. The fragmentation cost is bounded. A sequence wastes at most one partial block, so the waste is bounded by 16 positions × 327,680 bytes = 5,242,880 bytes per sequence, and the average is half that. A contiguous allocator that reserves the maximum length up front wastes the difference between reservation and use instead, and for a request that declares 32,768 tokens and generates 200, that difference is most of the per-stream slice.

Fairness is the second decision. First-come-first-served is simple and predictable, but a long generation can occupy a batch slot for a long time and, once the batch is full, delay every arrival behind it. Shortest-remaining-first lowers mean latency, and it can starve. Work an example. Suppose a long request has 200 tokens left and each decode step costs 10.4 ms of memory time, so the long request needs about 2.1 seconds of service. Now a stream of 10-token requests arrives every 50 ms. Each short request needs 10 × 10.4 ms = 104 ms of stream time, so the arrival rate exceeds the service rate and the queue never drains. The long request waits forever. A per-step prefill cap bounds the damage in the other direction, because no single admission can add more than C tokens of prefill compute to a step, and a scheduler that also ages queued requests eventually runs the long one.

### Prefix caching, throughput, and the reservation tradeoff

Prefix caching changes the scheduler's workload before the scheduler sees it. The engine matches a new prompt against blocks already resident in the pool. A hit means the KV for that prefix is already computed, so the prefill job shrinks from L tokens to L minus the matched length. The projections and attention for those matched tokens are skipped, their KV blocks are reused in place, and the kernel starts at the matched length to compute only the suffix. Attention for the suffix reads the cached prefix blocks alongside the new ones. A 100,000-token prompt that matches 65,536 cached tokens prefills 100,000 − 65,536 = 34,464 tokens. The saving counts as wall-clock time only when the machine would otherwise have been busy with that work.

The throughput payoff is real and bounded. Aggregate decode sums the tokens per second across all active streams. Four streams in one step emit four tokens and read four caches, while the weight read is shared, so aggregate throughput rises and the per-stream rate falls. The ceiling is 4/(1+3f) with f the KV share at batch one; at f = 0.4 it is 1.8×. The mechanism shows up per step. At batch one a step emits one token for one weight read and one cache read. At batch four the step emits four tokens for the same weight read plus four cache reads, so the weight read is amortized and the cache traffic is not.

Admitting one more stream costs almost nothing until the 16-row width fills. The kernel launches in the same shape whether it holds 4 rows or 16, and the 12 padding rows at concurrency four consume registers and issue slots but no KV bytes, so the step time does not grow in proportion to the row count. Past 16 rows the kernel runs a second wave, and each wave re-reads the weights, so the step time roughly doubles. What grows before that point is KV traffic, because every step reads the cache of every resident sequence, and those reads all come out of the same memory bus. Continuous batching recovers the waste static batching creates. It does not manufacture bandwidth.

Any throughput figure needs its definitions beside it. Time to first token runs from request arrival to the first sampled token and is dominated by prefill on long prompts. Decode duration runs from the first token to the last and scales with the reply length. Aggregate tokens per second is the sum over active streams, so it rises with concurrency while per-stream latency falls. A number quoted without its concurrency and its prompt length describes a workload, not a model.

My view is that continuous batching is the most consequential serving idea of the last several years, and it lives in the scheduler. Orca's contribution was noticing that the batch is a queue. The part I would argue with is the equal-split reservation. Reserving 32,768 tokens of reply budget for every stream at admission is simple, and it throws away capacity when requests are short, since a typical request generates 200 tokens. A scheduler that sized each reservation to the request's declared budget and rebalanced as sequences retired would fit more streams into the same 262,144 positions. This engine chose predictability, and the cost of that choice is measurable in the gap between 32,768 reserved positions and the 200 tokens a typical request actually uses.
