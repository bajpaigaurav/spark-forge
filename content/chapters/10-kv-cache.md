## Why generation is slow and memory-hungry

### The request profile this book assumes

Take a request carrying a 100,000-token prompt and asking for a 600-token reply. Prefill processes all 100,000 tokens in one pass. Decode then runs 600 passes, each producing one token and each reading the cache built so far. The asymmetry between those two phases is the subject of this chapter.

Time to first token is not the same as prefill time. It starts when the request arrives, so it includes admission wait, tokenization, the prefill pass, and the first decode step that emits a token. Prefill itself is one batched pass whose cost grows with prompt length; the first token adds one decode step on top. Once generation starts, each subsequent token costs a full decode step, so the per-token latency during decode is set by the memory-bound roofline rather than by the arithmetic.

### Why decode advances one token at a time

Prefill advances the whole prompt in one pass; decode advances one position per pass. The gap between the two rates follows from that shape rather than from a hardware defect.

A language model produces one token per forward pass. It reads the sequence so far, produces a distribution over the vocabulary at the final position, samples from it, appends the sample, and starts again. Token t+1 depends on token t, and token t did not exist when the pass began, so the loop cannot be unrolled in the naive exact-sampling sense — each token must be conditioned on the verified prefix. Techniques such as speculative decoding can propose several draft tokens and verify them in one target forward pass, partially breaking this dependency, but the target model still advances one verified block at a time. A 600-token reply is 600 forward passes, each conditioned on everything before it.

The naive way to run that loop feeds the whole sequence in every time. Pass one sees 100,000 tokens, pass two sees 100,001, and the last pass sees 100,599. Attention inside each pass lets every position attend to itself and all preceding positions, so the number of comparisons in one pass grows with the square of the sequence length. Summed over the reply, the total grows as the reply length times the square of the prompt length. For a long prompt that product is catastrophic. The model would re-derive the same key and value vectors for the same 100,000 positions 600 times and discard each set.

### What the KV cache stores

The fix is to keep them. Inside every attention layer, each position produces a query, a key, and a value. The query is consumed once, in the pass that created it. The key and the value are what later positions compare against and read from. So the cache stores exactly those two, per layer, per position, per key-value head, which is why it is called the KV cache and not the QKV cache. The omission of the query is the whole point. It is the one tensor with no future.

To see the shapes, take one layer with h query heads, g key-value heads, and head dimension d. The hidden state at a position projects to a query of h×d numbers, a key of g×d numbers, and a value of g×d numbers. When g equals h the layer is ordinary multi-head attention. When g is smaller, several query heads share one key-value head, which is grouped-query attention. The cache holds the keys and values only, so its size per position per layer is 2 × g × d × b bytes, where b is the number of bytes per element.

With the cache, pass k computes keys and values for one new position, then attends that position's query against the stored keys of every previous position. The feed-forward work per step is one token's worth. The attention work per step is a read over the cache. Generating n tokens after a prefill of length p costs roughly one prefill plus n small steps instead of n full passes. The transformer paper described the decoder as autoregressive from the start (Vaswani et al. 2017), and caching the keys and values is the standard way to run that decoder.

### The arithmetic behind the cache size

Now the size. The cache per position is 2 × L × g × d × b bytes, where L is the layer count, g the KV head count, d the head width and b the element size. Take Llama 2 70B: 80 layers, 8 KV heads at 128 dimensions, and two bytes per element in FP16. Each layer holds 8 × 128 = 1,024 values per position, keys and values across 80 layers come to 2 × 80 × 1,024 = 163,840 values per position, and at two bytes each that is 327,680 bytes per position, a third of a megabyte. At a 131,072-token context the cache is 131,072 × 327,680 = 42,949,672,960 bytes = 42.9 GB, which is most of a 192 GB H100 once the 140 GB of FP16 weights are loaded. That is why the same model in four bits leaves room for long context and in sixteen bits does not. The same multiplication answers the other sizes. A 100,000-token prompt needs 100,000 × 327,680 bytes = 32,768,000,000 bytes, or 32.77 GB. The pool's 262,144 positions would hold 262,144 × 327,680 bytes = 85,897,216,000 bytes, or 85.9 GB, and the native 1,048,576-position window would hold 1,048,576 × 327,680 bytes = 343,597,383,680 bytes, or 343.6 GB. Four concurrent 100,000-token streams would need 4 × 32.77 GB = 131.1 GB, which is more than the card has spare beside its FP16 weights.

The multiplier on g matters here. A model with 32 query heads and 8 key-value heads pays one quarter of what the same model would pay with 32 key-value heads, because the cache scales with g and not with h. That ratio is why grouped-query attention became standard, and it is what makes long context affordable at all. Every decode step re-reads the whole cache for its stream, so cache size sets the floor on step time as well as on memory.

### Positions, rows, and admission

The pool itself is a shared resource. It holds 262,144 positions across 4 concurrent streams. Positions, tokens, and rows are three different things and the rest of this chapter depends on keeping them apart. A token is a unit of text. A position is one slot in the pool holding that token's key and value for every layer. A row is one entry in a decode batch, and the book assumes a round batch of at most 16 rows per step.

The allocator is paged, following the design Kwon and colleagues described for vLLM in 2023. The pool is divided into fixed-size blocks, typically 16 positions each, and a block table maps each request's logical positions onto physical blocks. A request that grows does not need contiguous space, so the pool does not fragment the way a contiguous allocator would. The analogy to virtual memory is exact. The operating system maps contiguous virtual pages onto scattered physical frames through a page table, and the serving engine maps contiguous logical positions onto scattered physical blocks through a block table. That is what chapter 13 means by the page table fixing the allocation problem.

Admission reserves the reply budget before generation starts. The scheduler admits a request only if the pool can supply blocks for the prompt plus the reply budget, which is a worst-case reservation so that a request never stalls mid-reply waiting for cache. With four streams an equal share of a 262,144-position pool is 65,536 positions each, though the pool is shared and a stream may use more if others use less. The reservation subtracts 32,768 for the reply, 16 for the round batch, and 2 for alignment, leaving 32,750 usable positions per stream. A 100,000-token prompt does not fit that ceiling, so it cannot be admitted at concurrency 4 at all. At concurrency 1 the whole pool is available: 262,144 − 32,768 − 16 − 2 = 229,358 positions, and the prompt needs 100,000 of them against that ceiling, leaving 129,358 spare. It fits with room to grow.

### Batching, bandwidth, and the prefix cache

Decode is not compute-bound. The arithmetic per step is tiny: one token's worth of multiply-adds against a cache that may be hundreds of thousands of positions long, and against every weight in the model. Count the arithmetic intensity. Each weight participates in one multiply-add for the single new token, which is two floating-point operations, and it must be read from memory once, which is two bytes in half precision. That is one FLOP per byte. The KV read adds bytes and roughly proportional arithmetic, about one FLOP per byte in FP16, so it keeps the overall intensity near one rather than lowering it. The intensity sits near one, far below the balance point of peak throughput divided by bandwidth, which for an H100 is 295 FLOPs per byte.

The limit is therefore memory bandwidth. On an H100 that is 3,350 GB/s of HBM3, and a 70B model at four bits reads 35 GB of weights per token, so the floor is 35 GB / 3,350 GB/s = 10.4 ms per token, about 96 tokens per second for a single stream. The cache and the weights both have to come past the arithmetic units on every step, and a faster clock buys nothing because the units sit idle waiting on memory.

Prefill sits on the other side of the roofline. A prefill pass processes p tokens at once, so each weight read is amortized over p tokens. At p = 100,000 the intensity is roughly p FLOPs per byte, hundreds of times above the balance point of 295 FLOPs per byte, so the pass is compute-bound. That is why prefill and decode behave so differently on the same hardware: opposite bottlenecks.

Batching is the whole game in serving. Adding a stream does not cost four times the work, because the weight read is shared across the batch: one pass over the weights serves every row. That sharing is where the gain comes from. Each stream's cache read is separate, though, and the attention kernel walks rows one at a time, so the gain is never linear. Write the step time as a shared term A plus a per-stream term B times the stream count s. The speedup from one to four streams is 4(A + B) / (A + 4B), which is below 4 whenever B is not zero. At longer contexts the cache term grows and the multiplier falls further.

A prefix cache is the mitigation that costs nothing in quality. It matches the beginning of a new request against blocks already in the pool. Each block is hashed together with the hash of the block before it, so a match requires the entire prefix to be identical, not just one block. On a hit the allocator increments the block's reference count and points the new request's block table at the existing physical block. Eviction is least-recently-used among blocks whose reference count has fallen to zero. When many requests share a long system prompt or a retrieved document, most of the prefill is skipped. Nothing about the model changes. The same numbers are simply not computed twice.

The remaining cost is structural. The pool is fixed at 262,144 positions and shared, so context becomes a resource to be allocated rather than a property of the model. A stream that reserves 32,768 tokens of reply budget has reserved the cache for them whether or not it uses them, which is why the per-stream ceiling is 32,750 and not 65,536.

The KV cache began as an optimization and became the constraint. Multi-query attention, which Shazeer proposed in 2019, and grouped-query attention, which Ainslie and colleagues published in 2023, both attack the same multiplier in the formula, the number of key-value heads. State-space models such as Mamba (Gu and Dao, 2023) avoid a growing cache altogether, and the architectures that deploy at long context tend to carry some answer to the cache question. Nobody set out to make memory the bottleneck of inference. The field arrived there, then reorganized itself around it.
